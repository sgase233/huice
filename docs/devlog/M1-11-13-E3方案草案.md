### 1.1 VIS-AT-03 结果分布

### 1.5 待你本人在 ECS 执行的只读 SQL（不涉及密钥）

```sql
-- 1) 结果分布对账：每个 run 的分母与四态
SELECT r.id, count(*) AS total,
       count(*) FILTER (WHERE a.result = 'satisfied')            AS satisfied,
       count(*) FILTER (WHERE a.result = 'not_satisfied')        AS not_satisfied,
       count(*) FILTER (WHERE a.result = 'insufficient_evidence') AS insufficient,
       count(*) FILTER (WHERE a.result = 'conflict')             AS conflict
FROM assessment_run r JOIN assessment a ON a.run_id = r.id
GROUP BY r.id ORDER BY max(r.created_at) DESC LIMIT 20;

-- 2) 版本隔离：run 钉住的版本是否已落后于当前最新发布
SELECT a.run_id, a.policy_id, pv.version AS run_version,
       (SELECT pv2.version FROM policy_version pv2
         WHERE pv2.policy_id = a.policy_id AND pv2.review_status = 'published'
         ORDER BY pv2.reviewed_at DESC NULLS LAST, pv2.id DESC LIMIT 1) AS latest_version
FROM assessment a JOIN policy_version pv ON pv.id = a.policy_version_id
ORDER BY a.created_at DESC LIMIT 20;

-- 3) 轨迹阶段分布（确认在线/离线都有数据）
SELECT stage, count(*) FROM trace_step GROUP BY stage ORDER BY 2 DESC;

-- 4) 运行生命周期现状（D5 改造前的基线）
SELECT status, count(*) AS n,
       count(*) FILTER (WHERE finished_at = created_at) AS same_timestamp
FROM assessment_run GROUP BY status;
```

第 2 条若能查出 `run_version <> latest_version` 的行，就是 VIS-AT-01 历史版本切换的现成样本。

### 2.2 `policy_review_event`

```sql
CREATE TABLE IF NOT EXISTS policy_review_event (
    id                uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    policy_version_id uuid NOT NULL,
    policy_id         uuid NOT NULL,
    review_revision   integer NOT NULL CHECK (review_revision >= 0),
    actor_kind        text NOT NULL CHECK (actor_kind IN ('user', 'baseline', 'legacy_unknown')),
    actor_user_id     uuid REFERENCES app_user (id) ON DELETE RESTRICT,
    occurred_at       timestamptz NOT NULL,
    legacy_source     text CHECK (legacy_source IN ('reviewed_at', 'unknown')),
    created_at        timestamptz NOT NULL DEFAULT now(),

    CONSTRAINT policy_review_event_unique UNIQUE (policy_version_id, review_revision),
    CONSTRAINT policy_review_event_version_fk
        FOREIGN KEY (policy_version_id, policy_id)
        REFERENCES policy_version (id, policy_id) ON DELETE RESTRICT,
    -- 只有人工事件带操作者；基线与历史回填一律为空
    CONSTRAINT policy_review_event_actor CHECK (
        (actor_kind = 'user'     AND actor_user_id IS NOT NULL AND legacy_source IS NULL)
        OR (actor_kind <> 'user' AND actor_user_id IS NULL     AND legacy_source IS NOT NULL)
    )
);

CREATE INDEX IF NOT EXISTS policy_review_event_occurred_idx
    ON policy_review_event (occurred_at);
```

要点：

1. **`occurred_at` 用发布事务内的 `now()`**，不是路由入口的 `started_at`——与 `reviewed_at = now()` 同一时刻，跨午夜归日才有唯一答案。
2. **`review_revision` 恒为 1**：`publish()` 对已发布版本直接 409 `POLICY_ALREADY_PUBLISHED`（[storage.py:838-844](../../services/api/app/integrations/storage.py#L838)），现有流程一个版本只能发布一次。不实现「撤回重审」，`max+1` 不做；未来若支持，必须先改口径。
3. **`baseline` 用 `review_revision=0`**，与人工事件共存于同一 `policy_version_id`，唯一键不冲突。
4. 不把操作者写进 `trace_step`：轨迹表没有操作者列，且历史轨迹可能被清理；事件表是唯一真值。

### 2.3 基线命令（`collection_baseline`）

```sql
CREATE TABLE IF NOT EXISTS collection_baseline (
    id                  text PRIMARY KEY CHECK (id = 'default'),
    review_events_from  timestamptz,       -- 审核事件覆盖起点（T_review）
    run_lifecycle_from  timestamptz,       -- 运行生命周期覆盖起点（T_run）
    source              text NOT NULL CHECK (source IN ('reviewed_at', 'unknown')),
    note                text,
    created_at          timestamptz NOT NULL DEFAULT now()
);
```

**两个起点必须分开**（评审意见）：审核事件基线与运行生命周期来自不同批次（B3 与 B2），上线时间可以不同，不能共用一个 `T0`。未上线的那个留 `NULL`，对应指标整体返回 `not_collected`，**不返回 0**——旧运行记录只能代表「已记录的成功运行」，不能据此推断历史失败率。

一次性脚本 `infra/deploy/backfill-review-baseline.py`（用 venv 解释器跑，同 `issue-session.py` 的部署方式）：

1. `LOCK TABLE policy_version IN SHARE ROW EXCLUSIVE MODE`（跨事务持锁，见 §2.4 的锁用法）；
2. 已存在 `collection_baseline` 行 → 打印并退出 0（幂等，不重复写）；
3. 对每个 `review_status='published'` 的版本写一条 `actor_kind='baseline'`、`review_revision=0`：
   - `reviewed_at` 非空 → `occurred_at = reviewed_at`、`legacy_source='reviewed_at'`；
   - `reviewed_at` 为空 → `occurred_at = T_review`（本次执行时刻）、`legacy_source='unknown'`；
4. 写 `collection_baseline`：`review_events_from = T_review`、**`run_lifecycle_from` 保持 `NULL`**（由 B2 上线时另行写入），`source` 取「是否存在 `reviewed_at` 为空的行」的保守值：有一行为空就记 `unknown`；
5. 同一事务提交。

**基线事件不计 `reviewsCompleted`，只用于 `pendingAtEndOfDay` 的回放**；`review_events_from` 之前的日子按 §3.4 标 `partial`；`run_lifecycle_from` 为 `NULL` 时运行趋势整体标 `not_collected`。

### 2.4 运行生命周期改造

现状：`save_run()` 只在成功时插入一行，`created_at` 与 `finished_at` 写同一个值（[storage.py:1492](../../services/api/app/integrations/storage.py#L1492)、`:1512-1520`）；失败运行**不落行**；`guard_assessment_run_update()` 只允许改 `status`/`finished_at`（[001_init.sql:363-377](../../infra/sql/001_init.sql#L363)）。

改造后：

| 阶段 | 事务 | 动作 | 提交顺序 |
| --- | --- | --- | --- |
| 开始 | T1（独立提交） | `INSERT assessment_run (status='running', created_at=now())`；同一连接上取 advisory lock（key = run id） | `running` 必须**先提交**，后续事务才看得见这行 |
| 成功 | T2（独立提交） | 写 `assessment` + `assessment_dependency` + 快照，再 `UPDATE status='succeeded', finished_at=now()` | 先提交结果行，再提交状态 |
| 失败 | T3（独立提交） | `UPDATE status='failed', finished_at=now(), error_category=...`；不写任何 `assessment` | 评估异常时 T2 整体回滚，T1 的 `running` 行仍在 |
| 中断恢复 | 启动扫描 | `UPDATE status='interrupted'`，见下 | 只改已提交的残留行 |

上一版表格把「成功」写成「T1 继续」、把「失败」写成「T2」，与下面的独立事务要求自相矛盾（评审指出的不一致点）。**以本表为准**：`running` 提交后，结果与失败状态各自在独立事务保存。

几个必须写清楚的点：

- **`created_at` 就是开始时刻**，不新增 `started_at`。插行在评估前完成，`created_at` 即受理时刻；`as_of` 仍是用户传入的判断时点，两者不混。这直接回答 METRICS_SPEC §8.1 第 4 项。
- **`queued` 不落行**。现有实现没有队列，立即执行；契约里保留 `queued` 只为枚举稳定，但**契约描述必须改成「当前实现不产生 queued」**——现在 `contracts/openapi.yaml:3376` 附近写着「queued 只出现在 E1 起的新写入路径上（受理即落行）」，与代码不符，这是 VIS-05 的口径风险，必须一起改。
- **advisory lock 跨事务**：`pg_advisory_lock` 绑定连接，不能在 T1 `with conn.transaction():` 结束后仍假设锁还在。实现上把「插行 → 评估 → 落结果」包在同一个 `self._db.connection()` 上下文里，用显式 `BEGIN/COMMIT` 控制**三个**事务边界（T1 插行、T2 结果、T3 失败），退出前 `pg_advisory_unlock`。**锁的生命周期要单独验证**：T1 提交后锁仍被本连接持有、T2/T3 结束时才释放；若连接池把连接拿走，锁会跟着丢，测试要覆盖这一点。评估耗时可能较长，锁的是**单个 run**，不会串行化整个服务。
- **失败的事务必须独立**：评估抛异常时 T1 回滚会把刚插入的 `running` 行一起回滚；所以 T1 只能覆盖「插行」，评估与结果落库放 T2，失败在 T3 更新。这一点是和现有 `save_run()` 单事务写法最大的区别，实现时要先把 `orchestrator.assess()` 的调用点拆开，否则「先插 running」在异常路径上等于没插。
- **中断恢复必须三条同时满足**（[METRICS_SPEC.md:160](../product/METRICS_SPEC.md#L160)）：① 超时超过运行上限；② advisory lock 未被持有（`pg_try_advisory_lock` 能取到，取到后立即释放）；③ 原连接已断开。上一版草案只写了 ②，评审指出这会放走 ①③、把仍在跑的行误标。三条缺一不可，任何一条不成立都保持 `running` 不动。
  - **运行上限**：新增配置 `RUN_MAX_DURATION_SECONDS`，具体取值待 M2 定（建议 2 小时，覆盖 deepseek 抽取加规则评估的长尾）。不设硬编码常量，便于按部署调整。
  - **原连接是否断开**：按持锁的 pid 查 `pg_stat_activity`，查不到该 pid 即视为断开；查得到但状态不是 `idle in transaction`/`active` 的异常情形同样不置中断。
  - **防误标测试**（实现时先红后绿）：仍在跑的 run 不置中断；锁仍被持有的 run 不置中断；超时但连接仍在的 run 不置中断；三条全满足才置中断且不写 `error_category=internal`。
  - 单进程部署下扫描在 `lifespan` 里跑一次。文档与页面文案写「首版只覆盖单进程重启」；**多进程 advisory lock 不得被表述为已支持或已验证**。
- **`error_category` 只放分类，不放消息**：建议 `policy_not_published` / `model_unavailable` / `dependency_unavailable` / `internal`。禁止写堆栈、连接串、上游报文；详细原因仍走日志。
- **API-12**：`get_run` 先看 `status`，非 `succeeded` 一律 `409 RUN_NOT_COMPLETED`（与 API-13 同码，[assessment_runs.py:136-143](../../services/api/app/routes/assessment_runs.py#L136) 已有先例），**不要再 404**。行不存在仍 404 `RUN_NOT_FOUND`，两者从此可区分。这与 METRICS_SPEC §8.1 第 5 项对齐。
- 旧记录处理：`created_at = finished_at` 的行**保留原样**、不改写、不当作 0ms；耗时样本查询显式排除。

### 2.5 指标查询（不建每日快照表）

M3 的公式都是「事件回放」，不需要每日定时任务：

```sql
-- newDrafts：按 imported_at 归日
SELECT (imported_at AT TIME ZONE 'Asia/Shanghai')::date AS d, count(*)
FROM policy_version
WHERE imported_at >= %(from)s AND imported_at < %(to_exclusive)s
GROUP BY 1;

-- reviewsCompleted：只算 actor_kind='user'
SELECT (occurred_at AT TIME ZONE 'Asia/Shanghai')::date AS d, count(*)
FROM policy_review_event
WHERE actor_kind = 'user'
  AND occurred_at >= %(from)s AND occurred_at < %(to_exclusive)s
GROUP BY 1;

-- pendingAtEndOfDay：对每个 D，统计 imported_at < D+1 且没有 occurred_at < D+1 的事件的版本
-- 用 generate_series 生成日期，再 LEFT JOIN 聚合；不在应用层循环
```

`pendingAtEndOfDay` 的关键是**半开区间** `occurred_at < 次日 00:00:00`，不是 `<= 23:59:59`。SQL 里用 `date::date + 1` 转 `timestamptz` 时显式 `AT TIME ZONE 'Asia/Shanghai'`，避免服务器时区影响。

运行趋势同样按行聚合，`finished_at` 在查询时读取，所以跨午夜运行完成后，开始日的 `unfinished` 会自然变成 `succeeded`——不需要更新任何历史行。

### 2.8 测试清单（实现时先红后绿）

1. 发布成功 → 恰好一条 `actor_kind='user'` 事件，`occurred_at == reviewed_at`；重复发布 → 409 且事件数不变。
2. 发布失败（条件未通过校验）→ 事件数不变，事务回滚。
3. 基线脚本跑两次 → 第二次 0 写入；已发布版本各一条 revision=0。
4. `pendingAtEndOfDay` 的午夜边界：`23:59:59.999999` 导入 vs 次日 `00:00:00` 发布（METRICS_SPEC §2.3 的四个例子）。
5. 跨午夜运行：`23:55` 开始 `00:05` 成功 → 计入开始日、耗时 10 分钟、次日 total 不含。
6. 失败运行 → `failed` + `error_category`，API-12 返回 409 且响应不含堆栈。
7. 中断扫描（防误标四例）：仍在跑（锁被持有）不标；未超上限但锁空闲不标；超上限但连接仍在不标；三条同时满足才标 `interrupted`，且不改写 `finished_at` 之外的列。
8. 旧同值时间记录 → `durationSampleCount` 不计、`avgDurationMs` 不返回 0。
9. 时区：容器 `TZ=UTC` 下日统计仍是北京时间切日。
10. 契约守卫：`python contracts/generate_types.py --check` 在 M2 重生成前预期红，PR 里写明。

### 2.9 风险

- **最大风险是「先插 running」的回滚**（§2.4）。若不拆事务，「失败也落行」就是假的。实现顺序必须是：先拆 `assess()` 的调用边界，再加列，再改触发器。
- `interrupted` 只能处理「进程重启」；多进程部署要靠 advisory lock 判活，单进程部署靠扫描。文档要说清适用前提，不承诺分布式场景。
- 指标查询不做缓存；31 天上限内数据量小，先直查，出问题再加索引（`occurred_at` 已建）。

## 3. D4 数据侧方案

### 3.1 两种 scope，必须由请求固定

| scope | 版本集合来源 | `asOf` 来源 |
| --- | --- | --- |
| `profile`（画像页） | 当前所有 `review_status='published'` 政策的**最新版本**，**排除 `closed` 历史样本**（`COMPLETENESS_SPEC.md:25`）；排序规则与 `list_policies` 一致：`reviewed_at DESC NULLS LAST, id DESC` | 画像年度（默认「当前年 - 1」的申报年度），由请求显式传 `asOf` 或按画像年度推得；**不用服务器当天日期顶替**（`COMPLETENESS_SPEC.md:26`）。响应回写实际使用的值 |
| `run`（某次分析） | 该 run 的 `policyVersionMap` | 该 run 的 `as_of` |

两种口径**不能混**：同一个企业，画像页和 run 页的分母不同。响应必须带 `scope`、`asOf`、`definitionVersion`，否则结果无法复算。

- **排除 `closed` 与「所有已发布政策最新版本」的差异**（评审意见）：上一版草案没写排除，会把已关闭的历史政策算进分母。改为排除后分母变小，属于口径变更，必须体现在 `definitionVersion` 里，不能默默改。
- **`scope=run` 读的是当前事实，不是当时的事实**：固定政策版本与 `asOf` 只固定了分母，分子取决于 `enterprise_fact` 当下的行。响应与页面文案统一写「按该 run 的政策版本统计**当前**资料完整度」；要真正重现历史结果需要事实快照或事实版本链，本轮不具备，**不得宣称可重现**。

### 3.2 单位枚举与状态判定

单位 = `(FactKey, period_start, period_end)`。来源是 `rules.referenced_facts(expression, period=...)`（[rules.py:435-468](../../services/api/app/domain/rules.py#L435)），它已经能递归 `compare/date/industry_exclusion`，并把 `quarterly_average` 展开成 4 个季度 × 起止键——**不用重写 AST 遍历**。

判定顺序（先判适用性，再判填写）：

```
1. not_due                 ← 见下
2. not_applicable          ← v2 分支判定为「不可达」
3. applicability_unknown   ← v2 分支判定为「未知」
4. 行存在且值非空 → filled | filled_unverified（verified=false）
5. 行存在但值全空 → answered_unknown
6. 无行 → not_answered
```

`not_due` 的判定：**未定**（2026-11-13 评审明确暂不接受 A 或 B）。三个方案对照：

| 方案 | 规则 | 与 `COMPLETENESS_SPEC.md` 样例 E 的关系 |
| --- | --- | --- |
| A | 季度单位看 `quarter_start > asOf`；其余看 `period_start > asOf` | **冲突**：2026Q4 的 `quarter_start=2026-10-01 < asOf`，会被算进分母，而样例 E 要求 Q4 四个单位标 `not_due`、不入分母 |
| B | 一律 `period_end > asOf` | **也冲突**：同一 scope 的 `taxableIncome(2026)` 年度值 `period_end=2026-12-31 > asOf`，会被判 `not_due`，而样例 E 把 1 个年度单位算进了分母（适用 13 = 1 年度 + 12 季度） |
| **C（建议）** | 按期间粒度分层：季度类单位只算「已结束的季度」——`period_end > asOf` 即 `not_due`；年度/跨年类单位算「当前正在填的年度」——`period_start > asOf` 才 `not_due` | 与样例 E 一致：Q4 不入分母，`taxableIncome(2026)` 入分母 |

结论：这不是 A/B 二选一，样例 E 自身就同时要求两种处理。方案 C 需 M2/M3 在 `COMPLETENESS_SPEC.md` 里落成边界样例（季度期初、季度期末、年度三类各一条），定稿后写进 `definitionVersion`，M1 再实现。**在定稿前不实现 `not_due` 分支，也不把任何一版结果计入验收。**

**`verified` 必须直读库**：现在 `_normalized_fact()` 丢掉了 `verified`（[storage.py:2223](../../services/api/app/integrations/storage.py#L2223)），`to_wire_fact(fact, verified=False)` 让对外恒为 false（[profile.py:274](../../services/api/app/agents/profile.py#L274)）。完整度如果复用这条路径，`filled_unverified` 会和 `filled` 永远一样。**必须绕开 `_normalized_fact`，直接从 `enterprise_fact` 行读 `verified`。** 另外 `_UPSERT_FACT` 写入时把 `verified` 硬编码 `false`（[storage.py:174-179](../../services/api/app/integrations/storage.py#L174)），公开写入路径从不置 true——所以当前真实数据里 `verified` 恒为 false。这意味着 `filled_unverified` 在首版会是**唯一**的子状态，展示上不要把它渲染成「有问题」。

**行存在但四列全空**：`_load_facts` 已经保留这种行（[storage.py:1212-1221](../../services/api/app/integrations/storage.py#L1212)），`answered_unknown` 可判定，前提是读取时不做过滤。

### 3.3 适用性：v1 静态引用，v2 分支可达性

- **v1（`d4.static.v1`）**：scope 内所有条款的 `referenced_facts` 并集，全部算适用。分母偏大（分支不可达的键也算），但可复算。**不得表述为「零误判」**——把不适用项算进分母本身就是偏差，只是方向已知且恒定；评审已明确禁止这个措辞。
- **v2（`d4.branch.v2`）**：对每条条款做三值求值（`true/false/unknown`）：
  - `and` 子节点已知 false → 该分支下所有引用标 `not_applicable`；
  - `or` 子节点已有一个 true → 其余分支是否可达取决于运行时，本轮不猜，仍算适用；
  - 其余情况（含依赖缺失）→ `unknown` → `applicability_unknown`。

v2 需要「用当前事实做部分求值」，`rules.evaluate()` 现在是全有全无（缺值即 `INSUFFICIENT`），不能直接复用，要另写一个只回答「这个分支可能为真吗」的求值器。工作量约 1 人日。

**首版走 v1，评审已「有条件接受」**（2026-11-13）。条件：

1. 响应必须带 `definitionVersion="d4.static.v1"` 与 `applicabilityMode="static"`；
2. 页面图注固定写「**按政策引用统计，可能包含不适用项**」，不得写「零误判」，也不得把静态引用等同于实际适用；
3. 样例 B、C 的「适用性未知 / 分支排除」在 v1 下**不能宣称通过**，需 M3 另定过渡口径与验收范围；
4. 日后改适用规则必须升 `definitionVersion`，旧结果不重算。

## 4. VIS-06 日期来源核对

### 4.1 现状（代码与数据事实）

| 层 | 现状 | 后果 |
| --- | --- | --- |
| 表 | `policy_version` 只有 `published_at/effective_from/effective_to/application_window`（[001_init.sql:28-58](../../infra/sql/001_init.sql#L28)） | 没有地方存「这个日期是原文写的还是推算的」 |
| 导入 | `PolicyImportMetadata` 接收日期，无 provenance（[schemas.py:76-90](../../services/api/app/schemas.py#L76)） | 审核员无法在导入时标注可信度 |
| 契约 | `PolicySummary`/`PolicyDetail` 同样只有裸日期（[schemas.py:438-449](../../services/api/app/schemas.py#L438)、`:224-242`） | 前端只能显示「有值」，无法区分「已核实」 |
| 登记表 | `data/policies/source_register.csv` 的 9 行里，HIGHTECH/RD-SUBSIDY 的 `effective_to` 是推算，SMART/GREEN 的有效期原文未单列 | 有真实样本可回填，但没有列能承载 |
| 状态 | `closed` 混同「有效期已过」与「窗口关闭」（[storage.py:65-75](../../services/api/app/integrations/storage.py#L65)） | 页面把两种都写成「申报窗口已关闭」 |

### 4.2 五值状态（合并 M3 两份文档的口径）

| 值 | 含义 | 允许同存日期值 |
| --- | --- | --- |
| `verified` | 原文明确写着，且能定位到 source + locator | 是 |
| `derived` | 由期限/替代关系推算（如「施行 5 年」） | 是 |
| `unverified` | 有值，但原文未单列或尚未核实（登记表填的） | 是 |
| `unknown` | 未取得或原文未给 | **否**（值为 null） |
| `not_applicable` | 该日期对该政策不成立（税收制度性政策无申报窗口） | 是（窗口为 null） |

取值优先级：`verified > derived > unverified`，同一字段只有一个状态。**默认规则**：

- 导入时未显式标注 → `unverified`（有值）或 `unknown`（空值）；
- 只有同时给出 `sourceId` + `locator`、**且该 source 能关联到对应的政策版本**，才允许 `verified`，否则服务端拒绝（422），不允许「自称已核实」。第三项是评审补的：能定位还不够，要确认定位到的就是这个版本的原文（`policy_source` 与版本绑定，防止回填时把旧版或别的政策的条号挂上来）。

### 4.3 存储：`date_provenance jsonb`

不新增多列，用一个 jsonb 挂在 `policy_version` 上（与 `application_window` 同为 jsonb，迁移成本最低）：

```jsonc
{
  "version": 1,
  "effectiveFrom": { "status": "verified", "sourceId": "...", "locator": "第一条" },
  "effectiveTo":   { "status": "derived",  "basis": "施行 5 年", "derivedFrom": "2026-02-24" },
  "applicationWindow": { "status": "not_applicable" },
  "note": "附件 1 第一批/第二批"
}
```

- `sourceId` 指向 `policy_source` 行，`locator` 是章/条/页码；有 `sourceId` 才能回到原文，符合「可追溯」。
- `note` 承载**多批次说明**：首版不把 `application_window` 改成数组，用 note 写「第一批 2025-06-13—06-30；第二批 06-20—07-07」，页面必须原样显示，不能静默压平。
- 迁移 `011` 里加列，存量行按 §4.4 回填；未回填的行读出来是「默认值」，见下。

### 4.4 回填与验收样本

### 4.5 契约改动

1. `PolicySummary`/`PolicyDetail`/`PolicyDraft` 增加 `dateProvenance`（对象，见 §4.3），**必填**——缺省由服务端补默认值，不让前端猜。
2. `PolicyImportMetadata` 增加可选的 `dateProvenance`；不传就用 §4.2 的默认规则。
3. 新增派生字段 `temporal`（建议值 `open/closed_by_window/closed_by_expiry/expired/unknown`）用于替代现在混同的 `status='closed'`；`status` 保持原值不动，避免破坏既有调用方。
4. 版本升 `1.2.0-rc.1`：新增字段 + 新端点，M2 必须重生成 `apps/web/src/api/types.ts` 并同窗发布。当前 `generate_types.py --check` 是绿的，改动后在这之前会红，PR 里要写明。

### 4.6 遗留风险

- **多批次窗口**首版只靠 `note`，不是结构化数据；VIS-AT-04 的「两条网络 + 两条书面」只能文字表达。若 M2 要画两条时间轴，必须把 `application_window` 扩成数组，那是另一次契约变更，本轮不做。
- 公开详情页会把 `dateProvenance` 返回给 demo 身份；其中只含状态、条款定位和 note，不含内部审核意见，可以公开。
- HIGHTECH 的年度指南一旦取得，`unknown` 要能被改成 `verified` 并保留旧值——**需要一次「重新导入新版本」**，不能在原版本上改（已发布版本不可变）。这条要写进操作手册。
