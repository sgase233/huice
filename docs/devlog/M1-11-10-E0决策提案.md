## D1 鉴权兼容、会话实现与有效期

### D1.1 四类凭证

| 凭证 | 谁在用 | 能做什么 | 绝对不能做什么 |
| --- | --- | --- | --- |
| 企业会话（DB） | 企业用户浏览器 | 本人企业的画像、事实、分析、报告、本人轨迹 | 读他人对象（一律 404） |
| 审核员会话（DB） | 审核员浏览器 | 全部业务数据**只读**（含有归属 run 的轨迹）、政策管理、候选与统计、**本人企业**的写操作与分析 | 修改他人企业事实；读取密码、密钥、会话凭据 |
| `ADMIN_TOKEN` Bearer | 部署脚本、curl、运维 | **E1 后只读**：`/admin/**` 查询、全部 run 轨迹、自检 | 任何写操作（含发布、导入、条件保存）；进入浏览器；作为前端构建变量 |
| `huice_demo_session` | 演示入口 | **仅 `owner_user_id IS NULL` 的合成企业**，业务能力完整（创建样本、发起分析、出报告、看轨迹）、政策库只读 | 任何有主数据；`/admin/**`；`/auth/**` |

**运维 Bearer 为什么降为只读**：`admin_token` 只能说明「用了哪条通道」，说不了「是谁」；即便把它记成一个 `actor_kind`，审核工作量趋势的分母仍然不可追溯。审核量趋势的分母必须对应到人，而运维令牌天然没有身份。E1 之后写操作一律走审核员会话；需要脚本发布时，用审核员账号登录换会话，不虚构操作者。

### D1.3 三类入口都走通「创建/获得画像 → 编辑 → 分析 → 报告」

| 角色 | 入口 |
| --- | --- |
| 企业用户 | 注册事务内创建并绑定唯一企业（**必须**提交 `EnterpriseInput` 四要素：合成企业名、事实期间、地区、行业）；注册后维护该企业、发起分析；再调 `POST /enterprises` 返回 409 `ENTERPRISE_ALREADY_BOUND`。画像不完整时按现有补问逻辑提示，不阻塞已填事实的分析 |
| 审核员 | 注册时 `enterprise` 字段**可选**：提交则在同一事务内创建并绑定，不提交则不绑定；未绑定时首次调用 `POST /enterprises` 创建（同样需完整 `EnterpriseInput`），之后与企业用户行为一致；对他人的企业保持只读。**此为与 `EXTENSION_INTERFACES.md` §3.2「注册创建企业」的统一口径：企业用户必填、审核员可选** |
| 演示 | 保留 `POST /enterprises` 创建无主合成样本：服务端**强制写入 `owner_user_id = NULL`**，忽略客户端任何归属字段；单次演示会话最多 20 条；无主样本不可被认领、不可转为有主 |

「只依赖前端隐藏」的口径明确不采用：四条限制（强制 NULL、数量上限、不可认领、不可转有主）都由服务端约束与唯一索引保证。

**三条入口的端到端用例（M2 第 4 条要求）**

| 用例 | 步骤 | 断言 |
| --- | --- | --- |
| 企业用户 | 注册（带 `EnterpriseInput`）→ 改事实 → `POST /assessment-runs` → `GET report.md` | 全链路 2xx；再次 `POST /enterprises` 得 409 |
| 审核员 | 注册（不带企业）→ `POST /enterprises` → 改本人事实 → 分析 → 报告 | 同上；另：`GET` 他人企业 200，`PATCH` 他人事实 404 |
| 演示 | 带 demo cookie 建样本（属主由服务端置空）→ 改事实 → 分析 → 报告 | 全链路 2xx；第 21 次创建 429；改有主企业 404 |
| 越权矩阵 | A 账号用 B 的 `enterpriseId` / `runId` 逐个调 `GET` / `PATCH` / `POST` / `report` / `trace` | 一律 404，响应体不含对方任何字段；日志中不得出现对方数据 |

### D1.4 会话

- `user_session`：`token_hash`（sha256）唯一；明文只进 Cookie，库内与日志内都不出现。
- Cookie `huice_session`：`HttpOnly; Secure; SameSite=Lax; Path=/api`；`APP_ENV=local` 时关闭 `Secure`。
- 有效期：绝对 **12 小时**（`SESSION_TTL_HOURS`），空闲 **30 分钟**滑动（`SESSION_IDLE_MINUTES`），先到者生效。
- 撤销：登出立即 `revoked_at`；改密撤销该账号全部会话；封禁撤销全部会话；过期会话由定时任务清理。

### D1.5 多凭据同时存在时的优先级

v4 的「取第一个通过校验的凭证」与「会话失效后 Bearer 生效」互相矛盾，改为真值表。核心规则：**只有「未提供」才轮到下一个；「提供了但无效」一律 401**，绝不静默切换——否则会从会话降级到 demo，把合成数据当成用户自己的数据。

| 会话 | Bearer | demo | 结果 |
| --- | --- | --- | --- |
| 未提供 | 未提供 | 未提供 | `401 UNAUTHENTICATED` |
| 有效 | 任意 | 任意 | **以会话身份为准**，忽略 Bearer 与 demo |
| 提供但无效/过期 | 任意（含有效） | 任意 | `401 SESSION_INVALID`，**不降级** |
| 未提供 | 有效 | 任意 | 以 Bearer 身份（E1 后只读） |
| 未提供 | 提供但无效 | 任意 | `401 TOKEN_INVALID` |
| 未提供 | 未提供 | 有效 | 以 demo 身份（仅无主数据） |
| 未提供 | 未提供 | 提供但签名无效 | `401 DEMO_SESSION_INVALID` |

权限与对象判定另起一层，不与上述混用：凭证有效但角色不够 → `403 ROLE_FORBIDDEN`；角色够但对象不属于本人 → `404 OBJECT_NOT_FOUND`；写操作缺 CSRF/Origin → `403 CSRF_REQUIRED`。

demo cookie 载荷增加 `sid`（16 字节随机，随 cookie 一起签名），用于区分「每个演示会话」。

**demo 的企业配额（服务端原子计数）**

```sql
CREATE TABLE demo_quota (
  sid_hash   text PRIMARY KEY,          -- sha256(sid)
  created    int  NOT NULL DEFAULT 0,
  expires_at timestamptz NOT NULL);

-- 创建无主样本前执行。首建与计数合成一条语句，避免「先查后插」在并发下丢计数：
INSERT INTO demo_quota (sid_hash, created, expires_at)
VALUES ($1, 1, $2)
ON CONFLICT (sid_hash) DO UPDATE
   SET created = demo_quota.created + 1
 WHERE demo_quota.created < 20 AND demo_quota.expires_at > now()
RETURNING created;                       -- 无返回行 → 429 DEMO_QUOTA_EXCEEDED
```

- **初始化**：`issue-session.py` 签发时即写入 `demo_quota` 行（`created=0`，`expires_at` = cookie 过期时间），上面那条 upsert 只是把 `created` 加一。
- **并发首次**：两个请求同时首建时，`ON CONFLICT DO UPDATE` 会串行化在行锁上，只有一个能加成功；另一个按 `created` 现值判断是否超限。
- **过期与清理**：`expires_at` 与 cookie 同生命周期；每日清理任务删除 `expires_at < now() - 1 day` 的行。
- **旧 cookie 没有 `sid`**：视为 `legacy demo`，**只读**（不能创建样本），返回 `403 DEMO_SESSION_LEGACY` 并提示重新签发；不为历史 cookie 补造 `sid`。
- **`issue-session.py` 变更**：签发载荷增加 `sid`，同时写 `demo_quota` 行；迁移与兼容清单里登记这一项。

### D1.6 CSRF（四类请求分别定义）

| 请求类型 | Origin | CSRF token |
| --- | --- | --- |
| `POST /auth/register`、`POST /auth/login` | **必须存在且与 `PUBLIC_ORIGIN` 同源；缺失或不匹配一律 403** | 不要求（此时无已认证状态） |
| 带会话 Cookie 的其它写请求 | 必须同源 | 必须带 `X-CSRF-Token` |
| 带 demo Cookie 的写请求 | 必须同源 | 不要求；改为 Origin + Referer 同源 + 限流（demo cookie 不由用户会话派生） |
| 带 Bearer 或不带凭证（CLI/curl） | 不校验 | 不校验 |

- `csrfToken` 存会话表列，登录响应与 `GET /auth/me` 都返回**同一个值**，刷新页面后从 `/auth/me` 恢复，不做轮换（首版）。
- 上一版「无凭证请求不校验」只针对上表第四行，注册/登录属于第一行，不适用。

### D1.7 限流

- 部署确认是**单 worker**（`huice-api.service` 注释写明），进程内计数可用。
- 阈值：`IP` 维度 5 次/分钟、连续 20 次失败锁 15 分钟；`username` 维度只计数**不触发锁定**，避免他人恶意锁死某个账号。
- Redis 不可用时降级为进程内滑动窗口 + warning，不阻断；**重启清零**，接受该风险（演示期可接受，攻击面由外层 nginx `limit_req` 兜一层）。

### D2.4 回滚与数据隔离（撤销 v2 的「收口内网即可」）

旧应用不检查 owner，也不认识会话表；只收口公网、轮换令牌都不足以让有主数据不可见。**回滚时旧应用只连隔离副本库**，步骤如下（可执行，不是目标）：

1. **建副本库**：`CREATE DATABASE huice_rollback TEMPLATE template0;` ；`pg_dump -Fc` 全量导出 → `pg_restore` 进副本库（结构、触发器、函数随全量一起过去，`own` 归属为回滚账号）。
2. **临时关闭禁删触发器**（仅副本库）：`assessment_no_update_delete`、`assessment_run_no_delete`、`trace_step_no_update_delete`、`assessment_dependency_no_update_delete`、`invalidation_event_no_update_delete` 都会阻止删除。在副本库会话内执行 `SET session_replication_role = replica;`（需超级用户；不可用时改为逐表 `ALTER TABLE … DISABLE TRIGGER USER`，表所有者即可），清理完成后再恢复。
   **先断言再动手**：脚本开头检查 `current_database() = 'huice_rollback'` 且 `inet_server_addr()` 不是生产实例，任一不符立即退出，不允许在生产库上关触发器。
   注意 `replica` 模式同时会关掉外键触发器，删除顺序不再被约束兜底——所以第 5 步的引用检查是必做项，不是可选复核。
3. **按外键顺序清理有主数据**（副本库内，单事务）：`trace_step` / `assessment_dependency` / `invalidation_event` → `assessment`（`policy_version_id` 为 RESTRICT，政策不动）→ `assessment_run`（`enterprise_id` 为 RESTRICT，必须先删 run）→ `enterprise_fact` → `enterprise WHERE owner_user_id IS NOT NULL` → `app_user` / `user_session` / `review_event` / `discovery_*` / `policy_candidate`。
4. **对象存储先核对再处理**：先列真实对象键前缀，确认副本环境与正式环境是否共享同一桶/目录。**共享则一律不删不移**，只在副本配置里指向一个空的本地目录；不共享才把被删企业的 run 对象移入 `quarantine/`。两种处置都留清单。
5. **引用检查**：`assessment.policy_version_id` 全部指向存在的版本、`trace_step.object_refs` 无悬空引用、`enterprise.owner_user_id` 全为 NULL；各表行数与期望值对账。
6. **反向验证**：在副本库上以 demo cookie 与 Bearer 分别调用 `GET /enterprises`、`GET /assessment-runs/{id}`、`report.md`、`trace`，逐条断言 404 或空列表；同时验证**原库与原对象未受影响**（生产库行数不变、对象清单不变）。
7. **回滚期间产生的新数据**：副本库生成时刻记为 `t_dump`，新库在此期间保持离线只读；恢复新库后，`created_at > t_dump` 的账号数据单独保留不合并。
8. 记录：`t_dump`、关触发器范围、各表删除行数、对象处置清单、反向验证结果，作为回滚证据。

## D3 调度限制、抓取与候选轮换

### D3.1 三个时钟不是一回事

| 概念 | 取值 | 说明 |
| --- | --- | --- |
| timer 唤醒间隔 | 15 分钟 | 只负责「去看一眼是否到点」，不做抓取 |
| 抓取周期 | 默认 24 小时，最短 6 小时 | 审核员在后台配置；6 小时只是下限，是否收紧由 M3 按真实来源评估 |
| 单次运行上限 | 30 分钟 | 超过即中止本轮并记 `timeout` |
| 运行互斥 | 会话级 advisory lock | **没有时间租约**，进程退出连接断开即自动释放 |

v2 的「10 分钟租约」与 30 分钟运行上限矛盾，已废弃：并发控制改用 PostgreSQL `pg_try_advisory_lock(key)`，由**持锁的那条专用连接同时承担本轮全部数据库写入**，持到本轮结束；进程崩溃时连接断开，锁自动释放，不存在「租约过期但任务仍在跑」。租约概念仅保留为运行记录的审计字段，不参与并发判定。

**锁与写共用同一连接**（v5 修正）：v4 靠「写前检查 `pg_locks`」，但检查与提交之间仍可能断连，检查通过不代表提交时还持锁。改成机制上消除这个窗口：

- 专用 psycopg 连接 C 持有 `pg_try_advisory_lock`，**并且所有数据库写入都走 C**（候选写入、运行状态更新）。抓取（HTTP）用别的连接或不需要连接，不参与锁。
- 事务在 C 上提交，前提是 C 存活；C 一旦断开，未提交事务自动回滚、锁自动释放。因此**「锁已释放但旧任务仍提交成功」在机制上不可能发生**，不需要事后检查。
- 事务提交失败（`OperationalError`）→ 置 `abort`，停止后续抓取，本轮记 `failed` + `error_category='lock_lost'`，不重连取锁（避免与新任务并行）。
- 仍需保留 `SELECT 1` 探活，但用途只是**尽早**发现断连以减少无效抓取，不作为并发正确性的依据。
- 必须覆盖的测试：长任务（> 单次运行上限）、锁连接被杀、进程被 `SIGKILL`、第二个进程竞争接管、断连后重新执行。断言：任何时刻最多一个运行在写候选；旧任务不会在失去锁后提交任何数据。

### D3.2 抓取与容量

单页 15s；单响应 2MB；同站间隔 ≥2s；全局并发 1；单轮最多 50 个新候选；重定向最多 5 跳且每跳复检白名单。仅允许 `data/policies/source_register.csv` 登记的官方域名及子域；每次重定向与最终解析 IP 复检，禁止回环、内网、链路本地与 DNS 重绑定。

### D3.3 模型预算

单次运行 50,000 token、单候选 8,000 token，超限停止并记 `budget_exceeded`，不静默截断；`tokensUnknown` 时标记未知并停止继续消耗。**两个数是初始值，需 M3 用首批真实页面与附件实测校准后回填**；运行上限按实测确定，不与锁时长绑定。

### D3.4 停机补跑

最多补跑一次最近到期任务，记录 `late_by`；不追历史周期。

### D3.5 提交、幂等与轮换

**幂等四种返回**

| 情形 | 返回 |
| --- | --- |
| 同键 + 同请求指纹，已成功 | 返回原结果（同一 `201` 响应体） |
| 同键 + 不同请求指纹 | `409 IDEMPOTENCY_KEY_REUSED` |
| 同键，首次请求仍在进行中 | `409 IDEMPOTENCY_IN_PROGRESS`（可重试） |
| 并发首次提交，原子占用失败 | 同上 `409 IDEMPOTENCY_IN_PROGRESS` |

**执行顺序**：鉴权 → 查幂等键与指纹 → 命中已成功返回原结果（不看候选状态与 ETag）→ 未命中才 `SELECT … FOR UPDATE` 锁候选、校验 `status='pending_review'` 与 ETag、原子占用键。

**轮换事务**：`UPDATE policy_candidate SET status='expired'` 与 `INSERT INTO discovery_run` **在同一事务内提交或一起回滚**，且该事务在持锁连接 C 上执行（见 D3.1）。运行失败时旧候选仍为 `expired`，不自动恢复。

**可区分的终态**：`no_new_policy` / `fetch_failed` / `partial_failed` / `budget_exceeded` / `oversize` / `timeout` / `lock_lost`（见 D3.1）。

**待确认（M3）**：首批网址与栏目入口样本、附件大小分布（校准 2MB 与预算）。

## D5 事件、快照与运行生命周期采集

### D5.1 审核完成事件

- `review_event(policy_version_id, review_revision, actor_kind, actor_user_id, occurred_at, legacy_source)`，唯一键 `(policy_version_id, review_revision)`，幂等重放不重复计数。
- **`actor_kind` 统一为三值**（v5 修正，M2 第 2 条；v4 的枚举漏了 `baseline`）：

  | 取值 | 含义 | `actor_user_id` |
  | --- | --- | --- |
  | `user` | E1 之后由审核员会话发起的发布 | 必填 |
  | `baseline` | 上线事务 `T0` 生成的「当时已发布」状态快照，**只证明状态，不证明发生时刻** | NULL |
  | `legacy_unknown` | 上线前发生、只能确认「有过审核」但无法追溯到人的历史记录 | NULL |

  约束：`actor_kind='user'` ⇒ `actor_user_id NOT NULL`；`actor_kind IN ('baseline','legacy_unknown')` ⇒ `actor_user_id IS NULL`。
- `admin_token` **不进入枚举**：Bearer 在 E1 后降为只读，不再产生写事件；历史上用运维令牌留下的痕迹归入 `legacy_unknown`，不虚构账号。
- `review_revision` 取值规则（M1 机制口径，语义仍需 M3 确认）：`0` 预留给 `baseline`；同一 `policy_version_id` 的第一条 `user` 事件为 `1`，之后 `max+1`。`legacy_unknown` 若需回填，按发生顺序从 `0` 起补号，且不计入 `reviewsCompleted`。
- 去重单位：按 `policy_version`，一次发布 = 一个事件。

### D5.2 日终待办量

- **时间字段更正**：`policy_version` 没有 `created_at`，实际列是 **`imported_at`**。
- 状态出口只有发布：`review_status` 三态 `pending_parse / pending_review / published`，「已截止」是读取时派生、不落库。因此：
  `pendingAt(T) = count(policy_version where imported_at <= T and 不存在 occurred_at <= T 的发布事件)`
  该公式对 `T < T0` 同样成立，只是此时的事件来自基线、可信度按下面的分级降为 `partial` / `null`。
- **上线基线（v4 新增，v5 修正，M2 第 1、2 条）**：只从 `collectionStartedAt` 起采集新事件是不够的——上线前已发布的版本没有事件，会被「已导入且无发布事件」公式误算成待办。上线时刻 `T0` 必须在**同一事务**内完成三件事：
  1. `LOCK TABLE policy_version IN SHARE ROW EXCLUSIVE MODE`，阻止基线期间发生发布；
  2. 对 `review_status='published'` 的全量版本写入 `review_event`，`actor_kind='baseline'`、`review_revision=0`，`occurred_at` 按下表取值——**任何情况下都不拿 `imported_at` 顶替发布时间**；
  3. 写 `collection_baseline(id, taken_at, published_count, pending_count, checksum)`。
  事务提交即 `collectionStartedAt`。基线之后，待办公式在上线前后一致成立。

  | 情况 | `occurred_at` | `legacy_source` |
  | --- | --- | --- |
  | `reviewed_at` 非空 | `reviewed_at` | `reviewed_at` |
  | `reviewed_at` 为空 | `T0`（只声明「T0 时已发布」，不声明何时发布） | `unknown` |

  **为什么 `reviewed_at` 可以当近似**：`policy_version_reviewed` 约束（`infra/sql/001_init.sql:67`）保证 `published ⇒ reviewed_at IS NOT NULL`；`publish()` 在同一事务里写 `reviewed_at = now()`，且对已发布版本直接 `409 POLICY_ALREADY_PUBLISHED`（`storage.py:760`），所以它只会被写一次。但它**仍不是审核事件**：没有操作者、没有 `review_revision`、不保证经过应用写入。`unknown` 分支覆盖旧备份恢复、手工 SQL 等绕过约束的数据。

- **上线前历史按可信程度分级**（v5，M2 第 2 条）：

  | 区间 | 依据 | `availability` |
  | --- | --- | --- |
  | 日期 ≥ `T0` | `review_event` 精确事件 | `precise` |
  | 日期 < `T0`，相关版本全部 `legacy_source='reviewed_at'` | 基线事件近似 | `partial` |
  | 日期 < `T0`，任一相关版本 `legacy_source='unknown'` 且该日结果依赖它 | 无法确定 | 值为 `null`，`reason='LEGACY_PUBLISH_TIME_UNKNOWN'` |

- **`baseline` 事件不计入 `reviewsCompleted`**：它们不视为「可追溯的人工审核事件」。因此 `T0` 之前各日的 `reviewsCompleted` 一律返回 `null` + `reason='LEGACY_EVENTS_NOT_AUDITABLE'`，**不返回 0**（0 会把「不知道」伪装成「没有」）。
- 快照表降级为**每日校验记录**（与回放比对，不一致即告警），不再是唯一数据源。

**对账样例（M2 第 1 条要求）**：`T0 = 2026-11-20 10:00`

| 版本 | `imported_at` | 发布 | 事件 | 计为待办的区间 | 该区间可信度 |
| --- | --- | --- | --- | --- | --- |
| V1 | 11-01 09:00 | 11-02 15:00（上线前） | `baseline`，`occurred_at=11-02 15:00`，`reviewed_at` | 11-01 09:00 – 11-02 14:59（**曾待办 1 天多**，不是「永不」） | `partial` |
| V2 | 11-05 09:00 | 11-21 09:00（上线后） | `user`，`review_revision=1` | 11-05 09:00 – 11-21 08:59（跨 `T0`） | `T0` 前 `partial`，之后 `precise` |
| V3 | 11-20 10:30 | 未发布 | 无 | 11-20 10:30 起 | `precise` |
| V4 | 11-20 11:00 | 11-20 11:20（上线后） | `user`，`review_revision=1` | 11-20 11:00 – 11:19 | `precise` |

- `pendingAt(11-01 23:59)` = V1 = **1**，`availability='partial'`。
- `pendingAt(11-02 23:59)` = **0**，`availability='partial'`（V1 当天 15:00 发布；V2 尚未导入）。
- `pendingAt(11-20 23:59)` = V2 + V3 = **2**，`availability='precise'`（V1 的基线事件 `occurred_at ≤ T`，已排除；V4 已在 11:20 发布）。
- `pendingAt(11-21 23:59)` = V3 = **1**。
- `newDrafts(11-20)` = V3 + V4 = **2**（按 `imported_at` 归日）。
- `reviewsCompleted(11-20)` = V4 = **1**；`reviewsCompleted(11-01)`、`(11-02)` 返回 **`null`**，不返回 0。

上面的公式和基线事件一起把 V1 上线前的待办区间算了出来——这正是 v4 写「永不」错在哪：V1 确实待办过，只是那段时间在 `T0` 之前、只能标 `partial`。

- **数据库对账测试（M2 第 2 条要求）**：用上面四类版本做夹具，在真实 PostgreSQL 上跑「基线事务 → 回放查询」，断言与手算逐项相等：
  1. 上线前已发布（`reviewed_at=11-02 15:00`）→ 生成 `actor_kind='baseline'`、`legacy_source='reviewed_at'`；`pendingAt(11-01 23:59)=1`、`pendingAt(11-02 23:59)=0`，两日 `partial`；
  2. 上线前导入、上线后发布 → 跨 `T0` 的待办区间不被基线抹掉：`pendingAt(11-20 23:59)` 含 V2，发布后同版本归零；
  3. 上线后发布 → `actor_kind='user'`、`actor_user_id` 非空、`reviewsCompleted` 计 1；
  4. 负例一：把已发布行的 `reviewed_at` 置空（绕过 CHECK 的恢复数据）→ 事件 `occurred_at=T0`、`legacy_source='unknown'`，依赖它的上线前日期返回 `null` + `LEGACY_PUBLISH_TIME_UNKNOWN`；
  5. 负例二：SQL 层面断言不存在 `legacy_source='unknown' AND occurred_at <> T0` 的基线事件，也不存在 `legacy_source` 第三值——杜绝回退成用 `imported_at` 冒充发布；
  6. 负例三：`T0` 之前各日 `reviewsCompleted` 全部为 `null`，没有一条 `0`。

### D5.3 运行生命周期

- `POST /assessment-runs` 先独立事务插入 `status='running'`：`id / enterprise_id / as_of / status / fact_version / model_or_rule_version / created_at / user_id` 在分析开始前全部已知，`finished_at` 为空。
- `fact_version` 与事实快照在**同一读事务**（`REPEATABLE READ`）内取得，保证分析与版本标识对应同一份事实。
- 分析完成后，结果写入与 `status='succeeded'`、`finished_at` 同一事务；失败整体回滚并置 `failed`。
- `error_category` 用可空列，并放开 `guard_assessment_run_update` 对该列的更新（其余列仍禁止）。
- **运行级锁**：每个 run 在分析期间持有 `pg_try_advisory_lock(hashtext('huice.run:' || run_id))`，**锁与本次运行的写事务同连接**（同 D3.1），连接断开即锁释放且未提交写入回滚；正常结束时显式释放。
- **中断恢复**：单 worker + advisory lock 保证同一时刻只有一个实例在跑；启动扫描只处理**同时满足**三个条件的 `running` 记录：`created_at` 早于运行上限、`huice.run:<id>` 没有被任何连接持有、原连接已断开。三者缺一不得置 `interrupted`，避免误标正在运行的任务。因为锁与写同连接，「持锁者还活着」与「还有写入可能」是同一件事。
- 旧记录 `created_at = finished_at` 标为不可信耗时样本，查询按 `finished_at > created_at` 过滤。
- `API-12/13` 遇 `failed`/`unfinished` 返回 **409 `RUN_NOT_COMPLETED`**。
- 模型调用趋势本轮不做。

**待确认（M3）**：「审核完成」是否等同发布动作；`review_revision` 取值口径。

## 为什么契约草案单独出 PR

改动 `contracts/openapi.yaml` 会让冻结证据失效：评测指纹范围是 `services/api/app/**/*.py + contracts/openapi.yaml + requirements.lock`，当前冻结值 `8fe2368b…`（`EVALUATION_FREEZE.md` §5.2）。同时 `test_served_version_matches_the_contract` 锁死 `APP_VERSION == 契约 info.version`，单独改一侧会直接转红。

因此 E1 契约先落成独立草案文件（`contracts/openapi.e1-draft.yaml`），不进现行契约、不动 `APP_VERSION`；E1 后端实现完成后合并进 `openapi.yaml`，届时的版本号（拟 `1.1.0-rc.1`，同 D2.1 待签收）与指纹一起重算。**M2 已在 #54 同意这个做法**（「同意先用独立 E1 契约草案文件评审」），并要求草案明确基线、适用范围、版本与类型生成方式。版本号与各端点兼容结论仍待草案出来后共同确认。
