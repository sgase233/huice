> 边界：本文只覆盖现有 18 个 `FactKey`，不新增字段；材料清单（`material_requirements.csv`）不计入完整度，另列人工核查项。完整度只表示“适用字段是否填写”，**不代表政策资格、获批概率或材料齐全**。

## 1. 一句话口径

完整度 = **已填写的适用 `(FactKey, 事实期间)` 单位数** ÷ **适用单位总数**。

- 计数单位不是“18 个键各一格”，而是 `(FactKey, period_start, period_end)`。同一个键的不同年度、不同季度是不同单位。
- `0`、`false`、`verified=false` 都是**已填写**；`null` 和“没有这一行”都不是已填写。
- 不适用项不计入分母；适用性无法判断的项单列，**不猜成不适用**。
- 分母为 0 时 `ratio=null`，页面显示“不适用/无可统计字段”，不能显示 0% 或 100%。
- 只要存在任一“适用性待确认”项，**整图不显示总百分比**，只显示已填写数、适用数和未知项清单。分组可显示同一口径的计数，但不得用分组百分比暗示总体已完成。

## 2. 计算前必须固定的三个参数

没有这三个参数，完整度没有可复算的分母。VIS-01 的 `definitionVersion` 必须把三者一起记录。

| 参数 | 含义 | M3 建议 | 需谁确认 |
| --- | --- | --- | --- |
| `scope` | 本次统计参照的政策版本集合 | **画像页**：当前“机会列表”中状态为 `published` 的政策的最新版本；`closed` 历史样本不计入。**某次分析的完整度**：该 run 的 `policyVersionMap` 所指版本。两种口径不得混用。 | M1 确认接口能否接收/固定版本集合；M2 确认页面默认范围；三方确认 |
| `asOf` / 评估年度 | 判断“上年度”“本年度”“当前季度”的基准 | 画像页取当前画像年度；run 页取该 run 的 `asOf`。不得用查询服务器当天日期替代。 | M1/M2 |
| `definitionVersion` | 分组、适用规则、scope 口径的版本标识 | 本文定稿后写入；任何分组或适用规则变化都升版本，旧结果不重算。 | 三方 |

**为什么必须先定 scope**：同一个键在不同政策集合下适用性完全不同。例如 `equityFinancing` 只在专精特新的“营收低于 1000 万元”分支需要；`taxableIncome` 只被小型微利政策使用。先算“18 键填了几个”再解释，会把不适用的字段算进分母，得出无法解释的百分比。

## 3. 单位状态：六种，不是“填了/没填”两种

VIS-01 建议对每个单位返回下列状态之一。当前事实表允许“行存在但四个值列全空”（`001_init.sql` 注释为“未知”），所以**必须区分“答了不知道”和“根本没答”**。

| 状态 | 含义 | 是否入分母 | 是否入分子 | 页面文案 |
| --- | --- | --- | --- | --- |
| `filled` | 有该 `(key, period)` 行，值非空 | 是 | 是 | 已填写 |
| `filled_unverified` | `filled` 且 `verified=false`；是 `filled` 的子集，不另加分母 | 是 | 是 | 已填写（未核实） |
| `answered_unknown` | 行存在，但值为 `null`（如加计扣除“尚未申报/不确定”） | 是 | 否 | 已答：未知/尚未申报 |
| `not_answered` | 没有该 `(key, period)` 行 | 是 | 否 | 未填写 |
| `not_applicable` | 已判定该单位在 scope 内不需要 | 否 | 否 | 不适用 |
| `applicability_unknown` | 无法判断是否需要 | 否 | 否 | 适用性待确认 |
| `not_due` | 期间尚未到期（如本年尚未结束的未来季度） | 否 | 否 | 未到期 |

- `not_due` 是本期新增建议：小型微利的从业人数/资产总额要全年四个季度，但 2026 年尚未结束时，未来季度不能要求用户现在填写。把它们计入分母会让完整度在年初天然很低。**未来季度不入分母，页面注明“全年季度平均尚未完整，完整度只按已到期季度”**。该条需 M1/M2 确认。
- `filled_unverified` 不改变分子分母，只影响展示和提交前提示；不能把“未核实”当成“未填写”，也不能把“已填写”当成“已核实”。
- `answered_unknown` 与 `not_answered` 在分母中相同，但文案和补问优先级不同：前者是用户已明确“不知道/尚未发生”，后者是还没问过。

## 4. 分组建议（5 / 8 / 4 / 1）

M1 草案把 `creditRecord` 放入“基础信息”。M3 建议改为四组，把 `creditRecord` 单列。分组名称与归属需三方共同确认。

| 组 | 字段 | 数量 | 业务理由 |
| --- | --- | --- | --- |
| 基础与资质 | `region`、`industry`、`establishedDate`、`independentLegalEntity`、`specificMarketSince` | 5 | 来自营业执照/登记信息，变化慢，用户可在一次画像中确认 |
| 经营与财务 | `revenue`、`taxableIncome`、`rdExpense`、`assetsStart`、`assetsEnd`、`employeeCountStart`、`employeeCountEnd`、`equityFinancing` | 8 | 来自财务报表、纳税申报表和融资文件，按年度/季度取值 |
| 研发情况 | `rdActivity`、`rdExpenseIncrease`、`rdExpenseRevenueRatio`、`rdAddDeductionClaimed` | 4 | 研发活动与加计扣除口径，需财务/研发部门共同确认 |
| 合规与信用 | `creditRecord` | 1 | 动态状态，需在每次申报前重新核验，不能“填一次一直用” |

### 4.1 `creditRecord` 为什么建议单列

1. **时间语义不同**：其余 17 键是“某年度/某季度的历史事实”，`creditRecord` 是“本次判断时点的当前状态”。它按评估年度存一行，但状态可能在判断后变化；现有流程靠“提交前重新核验 → PATCH → 生成新 `factVersion` → 原 run 变 `stale`”补。放进“基础信息”会暗示“填一次就不用再管”，与这条流程冲突。
2. **来源不同**：它需要信用报告/信用中国/财政资金惩戒与超期未验收记录，不是财务报表或营业执照能直接带出；与“基础与资质”的登记类来源不同。
3. **业务作用不同**：它在研发投入补助、高企培育资助中都是硬门槛；`false` 是“明确不良好”的已填写事实，不是缺数据。单列能让用户看清“这是资格门槛，不是普通资料”。
4. **展示不同**：应显示“核验时间/来源”，并在提交前提示重新核验；混在基础信息里容易被当成静态字段。

**如果 M1/M2 坚持三组**：退而求其次放入“基础与资质”，但必须加“需动态复核”标识，并在提交前单独提示；这是次选，不是 M3 首选。无论归哪组，**不得把 `creditRecord=false` 当成未填写，也不得把缺失当成“记录良好”**。

## 6. `0`、`false`、`verified=false`、缺失与期间的对照

| 情形 | 示例 | 是否算已填写 | 说明 |
| --- | --- | --- | --- |
| 数值 0 | `taxableIncome=0`、`rdExpense=0`、`equityFinancing=0` | 是 | 真实零是事实；`rdExpense=0` 会让“研发费用>0”判不满足，但不影响完整度 |
| 布尔 false | `rdActivity=false`、`independentLegalEntity=false` | 是 | 明确否定是事实，不是缺失 |
| 诚信记录 false | `creditRecord=false`（不良好） | 是 | 资格上可能不满足，但完整度只问“填没填” |
| 未核实 | `verified=false` | 是 | 显示“已填写（未核实）”；不能算“已核实” |
| 无行 | 没有 `revenue` 的 2024 行 | 否 | 未填写；页面显示“未填写”，不显示 0 |
| 行存在但值为 null | `rdAddDeductionClaimed=null` | 否 | “已答：尚未申报/不确定”；不是 `false`，也不是未填写 |
| 不同年度 | `rdExpense` 2024 已填、2025 未填 | 2024 是，2025 否 | 同一键不同期间是两个单位；不能用 2024 顶 2025 |
| 不同季度 | `employeeCountStart` 2026Q1 已填、Q2 未填 | Q1 是，Q2 否 | 季度起止各成单位 |
| 未来季度 | 2026Q4 在 2026-11-10 尚未结束 | 否（`not_due`） | 不入分母；页面注明“未到期” |
| 不适用分支 | 成立不足两年时的 `rdExpenseIncrease` | 否（`not_applicable`） | 不入分母，不要求填写 |
| 适用性未知 | 营收未填时的 `equityFinancing` | 否（`applicability_unknown`） | 单列，整图不显示总百分比 |

## 7. 可手算的合成样例

以下均为**合成样例**，不对应真实企业；只用于 M1/M2 对照接口和页面。

### 样例 A：分母为 0

- **scope**：一个只含 `manual_review` 条件、且不引用任何 `FactKey` 的合成政策版本（或当前 scope 为空）。
- **单位**：无。
- **适用单位总数**：0；**已填写**：0；`ratio=null`。
- **预期展示**：“当前范围内没有可自动统计的画像字段；另有 N 项人工核查。”不得显示 0% 或 100%。
- **用途**：验证 VIS-01 的 `applicableCount=0` 与前端空态；防止把“没有可统计字段”误显示成“完整度 0%”。

### 样例 B：适用性未知（专精特新 scope）

- **scope**：`SZ-GRANT-SRDI-2025`；**asOf**：2025 年申报年度。
- **已填事实**：`region=440300`、`specificMarketSince=2022-05-01`、`independentLegalEntity=true`、`rdExpense(2024)=1,200,000.00`、`rdExpenseRevenueRatio(2024)=0.04`。
- **未填事实**：`revenue(2024)` 无行。
- **适用性未知**：`equityFinancing(2023-01-01/2024-12-31)`——营收未填，无法判断是否进入“营收低于 1000 万元”的 OR 分支。

| 单位 | 期间 | 适用性 | 是否已填写 |
| --- | --- | --- | --- |
| `region` | 2025 画像年度 | 适用 | 是 |
| `specificMarketSince` | 2025 画像年度 | 适用 | 是 |
| `independentLegalEntity` | 2025 画像年度 | 适用 | 是 |
| `rdExpense` | 2024-01-01/2024-12-31 | 适用 | 是 |
| `rdExpenseRevenueRatio` | 2024-01-01/2024-12-31 | 适用 | 是 |
| `revenue` | 2024-01-01/2024-12-31 | 适用 | 否（未填写） |
| `equityFinancing` | 2023-01-01/2024-12-31 | **待确认** | — |

- **预期分子**：5；**预期分母**：6；**未知项**：1。
- **预期展示**：“已填写 5 / 适用 6；另有 1 项适用性待确认（近两年股权融资）。”**不显示总百分比**。
- **注意**：`revenue` 是“适用但未填写”，必须入分母；不能因为它缺失就把 `equityFinancing` 判成不适用。

### 样例 C：`false`、`verified=false` 与分支排除（研发投入补助 scope）

- **scope**：`SZ-GRANT-RD-SUBSIDY-2026`；**asOf**：2026-11-10；成立日期 2022-03-01，按现有 AST 走“成立满两个会计年度”分支 A。
- **已填事实**：`region=440300`（`verified=false`）、`independentLegalEntity=true`、`establishedDate=2022-03-01`、`creditRecord=false`（明确不良好，`verified=false`）、`rdAddDeductionClaimed(2024-01-01/2025-12-31)=true`。
- **未填事实**：`rdExpenseIncrease(2025)` 无行。
- **不适用**：分支 B 的 `rdExpense(2025)` 与 `rdAddDeductionClaimed(2026)`。

| 单位 | 期间 | 适用性 | 是否已填写 |
| --- | --- | --- | --- |
| `region` | 2026 画像年度 | 适用 | 是（未核实） |
| `independentLegalEntity` | 2026 画像年度 | 适用 | 是 |
| `establishedDate` | 2026 画像年度 | 适用 | 是 |
| `creditRecord` | 2026 评估年度 | 适用 | 是（值为 false，明确不良好） |
| `rdAddDeductionClaimed` | 2024-01-01/2025-12-31 | 适用（分支 A） | 是 |
| `rdExpenseIncrease` | 2025-01-01/2025-12-31 | 适用（分支 A） | 否（未填写） |
| `rdExpense` | 2025-01-01/2025-12-31 | 不适用（分支 B） | — |
| `rdAddDeductionClaimed` | 2026-01-01/2026-12-31 | 不适用（分支 B） | — |

- **预期分子**：5；**预期分母**：6；比例 83.3%。
- **预期展示**：“已填写 5/6（83%）；诚信记录为‘不良好’但仍属已填写；2 项因适用分支不适用。”
- **注意**：`creditRecord=false` 不能算未填写；`verified=false` 不能算未填写；分支 B 的两个单位不能进分母。

### 样例 D：同一键不同期间（最小对照）

| 事实 | 值 | 是否已填写 |
| --- | --- | --- |
| `rdExpense` 2024 | 1,200,000.00 | 是 |
| `rdExpense` 2025 | 无行 | 否 |

若 scope 同时要求 2024 与 2025 两个年度，则该键贡献 2 个单位，分子 1、分母 2；不能因为“研发费用已填过”就算 2/2。

## 8. 待确认清单（按接收人）

### 8.1 M1 需要确认或实现

1. VIS-01 能否接收固定 `scope`（政策版本集合）与 `asOf`，并在响应中返回每个 `(FactKey, period)` 的上述六种状态。
2. 能否区分“行存在且值为 `null`”与“无行”（`answered_unknown` vs `not_answered`）；现有事实表允许四列全空，但读取层是否保留该行需确认。
3. 能否对 OR/AND 分支做可达性判断；若本轮不做，是否接受“按静态引用统计”并在 `definitionVersion` 标注。两种做法的分母不同，不能混用。
4. 未来季度 `not_due` 的判定：以 `period_end > asOf` 为准，还是以“自然季度是否结束”为准；需与现有季度展开逻辑一致。
5. `rdExpenseRevenueRatio` 是否由前端/后端自动计算并落事实行；若只计算不落库，完整度不能算已填写。
6. `creditRecord` 的核验时间是否可从 `factVersion`/失效事件带出；完整度是否只显示“当前版本”，不回溯历史核验。
7. 性能：一次返回 18 键 × 多期间的单位明细，是否需要分页/按组查询；首版数据量小，但不能用 `facts.length/18` 近似。

### 8.2 M2 需要确认或实现

1. 四组分组是否可落地；`creditRecord` 单列“合规与信用”是否增加页面复杂度。
2. 存在 `applicability_unknown` 时，整图不显示总百分比；分组只显示计数，不显示可能误导的百分比。
3. 分母为 0 时显示“不适用/无可统计字段”，不显示 0%。
4. `filled_unverified` 显示“已填写（未核实）”；`answered_unknown` 显示“已答：尚未申报/不确定”；`not_answered` 显示“未填写”；三者不能合并成“缺失”。
5. `not_due` 显示“未到期”，不与“未填写”混用；注明全年季度平均尚未完整。
6. 每个单位可定位到字段、期间、来源/核验状态；人工核查项单独成列表，不混入完整度分母。
7. 图注必须包含：“完整度只反映填写情况，不代表政策资格或获批概率。”

### 8.3 三方共同确认

1. 分组定稿（5/8/4/1）与 `creditRecord` 归组。
2. 默认 `scope`：画像页用“当前已发布政策最新版本”，run 页用该 run 的版本集合；`closed` 历史样本是否展示但不计入。
3. OR/AND 分支适用性规则：分支可达性判断 vs 静态引用统计；选定后写入 `definitionVersion`。
4. `specificMarketSince` 多细分市场的业务处理：单键是否足够；不足时转人工核查还是新增限定字段（新增字段会影响契约与迁移，本轮不擅自加）。
5. `rdAddDeductionClaimed` 三态与 RDSUB 分支 B“当年度”受理口径；后者仍需主管部门确认，当前期间只是标注口径。
6. 完整度清单的最终签认：需 M1、M2、M3 共同评审并留下记录；本文不代替任何成员签收。
