## 1. 可观测证据与覆盖判定（回答 D-3 / D-7）

覆盖等级**不是一个全局判断**，而是逐指标按「这一指标的有效采集区间有没有缺口」算：

| 证据 | 能证明什么 |
| --- | --- |
| `policy_version.imported_at` | 新草稿历来可读 → `newDrafts` 通常 `precise`（起点缺失时 `partial`） |
| 发布事件（B3 基线 + 后续事件） | 只覆盖 `T_review` 之后的**人工审核完成**；`T_review` 前 `not_collected` |
| `collection_baseline.run_lifecycle_from`（`T_run`） | 运行记录从这一刻起完整；之前 `failed`/`unfinished`/耗时 `not_collected`、`total`/`succeeded` 标 `partial` |
| `assessment_run` 的 `lock_owner_pid`/`started_at` | 只有 B2 之后的运行能判定「是否仍在跑」 |

**扫描关闭 ≠ 未采集**（保留这条事实）：运行记录在评估开始就写 `running`，与扫描开关无关；扫描只决定崩溃残留行会不会被标 `interrupted`。所以扫描关闭时这些运行仍计入 `total`/`unfinished`，不被排除。

**但覆盖等级不因此一律写 `precise`**——按实际缺口判：

| 情况 | 覆盖处理 |
| --- | --- |
| 采集中途启用 | 该指标在启用之前的部分 `partial`，`coverageFrom` 给启用时刻 |
| 部署回退 / 数据库不可用 | 该时段 `partial`，`reason` 写明；无法确认缺口的，返回 `null` + `reason`，不猜 |
| 扫描关闭期间的崩溃残留 | 计入 `unfinished`（覆盖仍按采集中），另给 `notes`：「中断恢复扫描未开启，残留运行会停在 running，`unfinished` 可能偏高」 |
| `T_run` 之前 | `failed`/`unfinished`/耗时 `not_collected`；`total`/`succeeded` 只能是「已记录数」并标 `partial` |

**无法确认时一律降级，不升格**：缺起点、缺事件、口径不清，就标 `partial`/`null` 并在 `reason` 写明，不用 0 或 `precise` 补。

### 1.1 覆盖缺口的证据来源（B3 方案，回应 M2 的两轮 P1）

三件事先说清：**缺口记录不能依赖出故障的那个数据库**、**迁移时间不等于采集开始**、**`interrupted` 是运行状态不是覆盖证据**。

#### 证据分两层

| 层 | 内容 | 为什么不依赖库 |
| --- | --- | --- |
| **主机侧事件日志** | `/var/lib/huice/collection-lifecycle.jsonl`：每次服务停止 / 启动、部署 / 回滚、人工维护，各追加一行 `{event_id, at, kind: stop|start|migrate|rollback|maintenance, note}`，`fsync` 落盘 | 文件在主机上，库挂了也能写；由 `huice-api.service` 的 `ExecStopPost` / `ExecStartPost` 与 `migrate.sh`、`rollback.sh` 调用 `infra/deploy/record-collection-event.py` 写入 |
| **库内采集起点** | `collection_baseline.review_events_from` / `run_lifecycle_from` | 由应用**真正能写库**时写入，代表「从这一刻起采集成立」，不是迁移时间 |

#### 区间怎么划

- **采集起点**：用 `run_lifecycle_from`（B2 启动时写）。为 `NULL` → 该指标 `not_collected`，**不从 `schema_migration` 的迁移时间推断采集成功**；
- **停止 → 启动**：日志里上一次 `stop` 到下一次 `start` 之间为缺口；`scope` 取 `run` / `review` / `all`；
- **只有 `stop` 没有 `start`（进程被杀、机器断电尚未恢复）**：`gap_to = NULL`，视为**未闭合缺口，持续到当前时刻**；
- **启动时补录**：服务起来后读取日志尾部，把缺的事件按 `event_id` 幂等导入 `013_collection_gap`（`ON CONFLICT DO NOTHING`），不重复、不丢；
- **首次部署前**：没有起点也还没写日志 → 全部指标 `not_collected`，不用 0 或 `precise` 充数。

#### 证据缺失时各指标怎么办

| 情况 | 指标返回 |
| --- | --- |
| 有起点、日志可读、窗口内无缺口 | 按指标正常给值，`state=precise` |
| 有起点、日志可读、窗口与缺口重叠 | 该区间 `partial`，`coverageFrom` 给缺口结束时刻，`reason` 写缺口原因 |
| 有起点、**日志缺失或不可读** | `partial` + `reason=GAP_EVIDENCE_MISSING`，不声称完整 |
| 无起点 | `not_collected`（`failed`/`unfinished`/耗时），`total`/`succeeded` 只能是已记录数并 `partial` |

**没有缺口记录不能证明没有缺口**：所以只要日志不可读或未闭合区间跨到窗口，就降级；`013` 与日志都只是「证据」，不是「保证」。

#### `interrupted` 与覆盖分开

`interrupted` 是**运行状态**（崩溃后被扫描标记的未完成运行），只影响 `unfinished` 计数与 `notes`，**不直接改变覆盖等级**。覆盖只由上面的起点与缺口证据决定；哪种证据影响哪个指标的覆盖，最终以 M3 在 `METRICS_SPEC` 的口径为准。

#### 谁维护

- **M1**：`infra/deploy/record-collection-event.py`、unit 钩子、`migrate.sh`/`rollback.sh` 调用、`013_collection_gap` 迁移与导入逻辑；
- **运维**：人工维护前后执行同一条命令补记；
- **M3**：定义「哪类缺口影响哪个指标的覆盖」，M2 按契约展示。

## 3. 响应样例与降级语义

### D-1 `dateProvenance`

```json
"dateProvenance": {
  "version": 1,
  "effectiveFrom": { "status": "verified", "source": "body", "locator": "第十七条「自印发之日起施行」", "note": null },
  "effectiveTo": { "status": "derived", "source": null, "locator": null,
                   "basis": "办法第十七条「有效期 5 年」；按 2026-02-24 起算得 2031-02-23，满 5 年口径可能差一日",
                   "derivedFrom": "2026-02-24", "note": null },
  "applicationWindow": { "status": "unknown", "source": null, "locator": null,
                         "note": "2026 年度窗口见年度申报指南；该指南不属于本版本来源，未标 verified" },
  "note": "申报窗口不得当作政策有效期；多批次窗口与办理方式见本条 note"
}
```

降级语义（回应 M2 的补充）：

| 情况 | 响应 | 页面 |
| --- | --- | --- |
| 旁表**无行** | `dateProvenance = null` | 显示「来源未记录」，不显示任何「已核实」 |
| **单个字段**在旁表里缺失 | 该字段对象为 `null`（如 `"effectiveTo": null`），不合成 `unknown` | 显示「该字段无来源记录」 |
| `status=verified` 但 `sourceId` 指向的来源行已不存在 | 读取时降级为 `{status:"unverified", source:null, locator:<保留>, note:"来源行已不存在"}` | 按未核实展示，不显示为已核实 |
| `source=attachment` 但该版本已无附件 | 同上降级 | 同上 |

写侧已有校验（`verified` 必须有 `source`+`locator`），读侧再做一次「来源行是否仍可解析」，避免库里数据被删后仍显示为已核实。

### D-3 指标响应（按指标覆盖）

```json

  "newDrafts": 2, "reviewsCompleted": 1, "pendingAtEndOfDay": 2,

    "reviewsCompleted":  { "state": "partial", "coverageFrom": "2026-11-20T10:00:00+08:00" },
```
