# 审核工作量与系统运行趋势业务口径（D5）

> **状态：M3 草案，2026-11-10；2026-11-13 增补 §9 对 M1 E3 方案的 D5 核对、对账数字与运行上限责任口径。待 M1、M2、M3 共同评审，未签收。** 本文给业务语义、边界条件与可手算样例；事件表结构、事务、查询实现由 M1 定，前端展示由 M2 实现。

> 边界：本文不规定数据库表名、SQL、迁移编号或接口字段；这些由 M1 在契约草案中确认。本文也不把“提案”写成“已签收”。

## 1. 三条总原则

1. **先有事件，再有计数**：审核完成必须有可追溯到人的事件；不能拿 `reviewed_at`、发布时间或日志条数替代。
2. **缺测不是 0**：未采集、部分覆盖、真实零必须分开；`null` 不得按 0 展示，0 也不得在未采集时返回。
3. **按业务发生时间归日**：审核事件按 `occurred_at`、运行按实际开始时间归入 `Asia/Shanghai` 的自然日；跨午夜不按结束时间改归日。

## 2. 三个审核指标的计数对象

### 2.1 新草稿 `newDrafts`

| 项 | 定义 |
| --- | --- |
| 计数对象 | 新建的 **policy version**（政策版本），不是 `policy` 政策条目 |
| 时间 | `policy_version.imported_at` 换算为 `Asia/Shanghai` 后归日 |
| 去重单位 | `policy_version.id`；同一版本只计一次 |
| 计入 | 手动导入生成的新版本；候选提交成功后生成的新版本；同一政策的新版本（新 `policy_version.id`） |
| 不计入 | 候选本身（未提交）；丢弃的候选；提交失败/回滚未留下版本；幂等重放未新建版本；仅编辑既有草稿/候选 revision |
| 边界 | 当天 `00:00:00` 计入当天；次日 `00:00:00` 计入次日；`imported_at` 是服务器写入时间，不是用户填的申报日期 |

**候选提交与丢弃**：提交成功 = 只创建草稿（pending_parse），**算一个新草稿**；随后人工编辑、抽取、保存条件都不再算新草稿。丢弃 = 不创建政策/版本，**不算**。提交失败 = 没有版本，**不算**。同一候选的幂等重放只返回原结果，**不重复计**。

**历史可用性**：`imported_at` 是现有列，历史上一般可读；但若旧数据被清理或迁移，覆盖起点需 M1 给出。页面应显示“统计自最早可读导入记录”而不是默认从上线日才有。

### 2.2 人工审核完成 `reviewsCompleted`

**当前业务中“人工审核完成”对应什么动作？**

现有流程只有 `pending_parse → pending_review → published` 三个持久状态，没有独立的“审核通过”状态。唯一把版本推进到 `published` 的人工动作是：

`POST /admin/policies/{policyId}/publish`（API-07），请求体带 `version` 和 `If-Match`。

`publish()` 在同一事务内：校验条件引用、校验原文存在、设置 `review_status='published'` 与 `reviewed_at=now()`、写 `human_review/approve` 轨迹、对已发布版本返回 `409 POLICY_ALREADY_PUBLISHED`。

**M3 业务意见（待 M1/M3 在 D5 确认）**：首版把“人工审核完成”定义为：

> **一名已登录、可识别的审核员，在政策审核页对某个 `policy_version` 执行“审核通过并发布”，且发布成功。**

发布成功可以承载该事件，但必须同时满足：

1. **有真实操作者身份**：来自审核员会话的 `user_id`，不是共享 `ADMIN_TOKEN`、不是 demo cookie、不是脚本或定时任务。
2. **与发布同一事务落事件**：发布成功与 `review_event` 写入同事务提交；发布失败/回滚不留下“已完成”。
3. **事件含版本、操作者、时间、来源**：至少 `policy_version_id`、`actor_user_id`、`occurred_at`、`review_revision`；不能用 `reviewed_at` 单独代替。
4. **幂等重放不重复计数**：同一 `(policy_version_id, review_revision)` 唯一；重复请求返回原结果，不新增事件。
5. **不是自动动作**：抽取、引用校验、候选提交、定时任务、基线回填都不算人工审核完成。

**当前不能直接拿什么当事件**：

- `reviewed_at`：它能证明“该版本曾发布”，但没有操作者、没有 revision，也不能保证经过应用写入；只能作为上线前基线的近似时间，不能作为 `reviewsCompleted` 的事件。
- 发布时间/`publishedAt`：与 `reviewed_at` 同源，同样缺操作者。
- `trace_step` 的 `human_review` 行：有 `human_action=approve`，但当前没有操作者身份，且历史轨迹可能被清理；不能单独作为可追溯事件。
- 候选提交：只创建草稿，不是政策审核完成。
- 日志：不是结构化事件，不能按日志行数计数。

**如果业务以后新增独立的“审核通过”动作**（先审批、后发布），本节定义要改为“审核通过事件”，不能继续把发布当审核完成；这是后续变更，不在本轮擅自扩展。

### 2.3 日终待办 `pendingAtEndOfDay`

| 项 | 定义 |
| --- | --- |
| 计数对象 | 正式 `policy_version` 存量，不是当天新增数，也不是候选 |
| 状态 | `pending_parse` 或 `pending_review`（未发布） |
| 公式 | `count(policy_version where imported_at < 次日 00:00:00 且不存在 occurred_at < 次日 00:00:00 的发布事件)`（按 `Asia/Shanghai`，半开区间 `[当日 00:00:00, 次日 00:00:00)`） |
| 去重 | 一个版本在一天最多计一次；已发布版本不再计 |
| 不含 | 未提交候选、已丢弃候选、已过期候选；历史已发布版本 |
| 当天未结束 | **`null`**，不返回当前存量；页面显示“今日尚未结算” |
| 缺快照/缺事件 | `null`，不用次日当前值补昨日日终 |

- 公式对 `T0` 之前也成立，但事件来自基线，可信度按 §5 降为 `partial` 或 `null`。
- 日终边界是 `Asia/Shanghai` 次日 `00:00:00` 之前，即半开区间 `[当日 00:00:00, 次日 00:00:00)`；`23:59:59.999`、`23:59:59.999999` 等更高精度的当天末时刻都属于当天。不得用 `<= 23:59:59.999` 截断，否则微秒/纳秒精度的时间戳会被漏掉。
- 若某版本在当天 `23:59` 导入、次日 `00:10` 发布：当天日终计入待办；次日日终不再计入。不能按发布时间把它从当天抹掉。
- 贴近午夜的边界例子：`11-20 23:59:59.999999` 导入的版本，在 `11-20` 日终计入待办；`11-21 00:00:00.000000` 导入的版本，在 `11-21` 日终计入待办。发布事件：`11-20 23:59:59.999999` 发布 → 该版本在 `11-20` 日终前已发布，不计入 `11-20` 日终待办；`11-21 00:00:00.000000` 发布 → 该发布事件不属于 `11-20` 的已发布集合，版本在 `11-20` 日终仍待办；到 `11-21` 日终时该版本已发布，不再计入。
- 已发布版本不能回退到待审（现有流程没有撤回状态）；若未来支持撤回，公式和事件需重新定义。

### 2.4 `review_revision` 的业务含义

**M3 业务口径（待 M1 确认机制）**：

- `review_revision` 是**同一个 `policy_version` 上人工审核完成事件的序号**，用于去重与幂等，不是“编辑次数”“抽取次数”或“审核轮次”的通用计数器。
- `0` 预留给上线基线（`actor_kind='baseline'`），只表示“`T0` 时已发布”，不是人工审核完成。
- 当前流程一个版本只能发布一次（重复发布 409），所以正常的人工事件只有 `review_revision=1`。
- 若同一政策导入新版本，新版本是新的 `policy_version_id`，其人工事件仍从 `1` 开始；不能把同一政策的多个版本累加成 revision 2、3。
- `legacy_unknown` 若需回填，可按发生顺序补号，但**不计入 `reviewsCompleted`**；补号只为审计，不改变业务计数。
- **待决**：如果未来允许同一版本“撤回重审/再次审核”，revision 才需要 `max+1` 并每次计入完成数。当前证据不足以确认该场景存在，**不擅自定案**；M1 若在实现中支持重审，必须先与 M3 确认业务含义。

## 3. 时间、边界与缺测

### 3.1 北京时间归日

- 数据库存 UTC；日统计统一按 `Asia/Shanghai` 切日，响应带 `timeZone:"Asia/Shanghai"`。
- 查询参数 `from`/`to` 是当地日期，首尾包含；首版最多 31 天（具体上限 E0 冻结）。
- 区间定义为 `[当天 00:00:00, 次日 00:00:00)`：
  - `00:00:00.000000` 属于新一天；
  - `23:59:59.999`、`23:59:59.999999` 等任何小于次日 `00:00:00` 的时间戳都属于当天；
  - 统一用“`< 次日 00:00:00`”判断，不用“`≤ 23:59:59.999`”或“`≤ 23:59:59`”——前者会漏掉更高精度时间戳，后者会丢毫秒。
  - 贴近午夜：`11-20 23:59:59.999999` 属于 `11-20`；`11-21 00:00:00.000000` 属于 `11-21`。

### 3.2 跨午夜

- 审核事件按 `occurred_at` 归日：`11-21 23:50` 开始审核、`11-22 00:10` 发布，计入 **11-22**。
- 运行按**实际开始时间**归日：`11-21 23:55` 开始、`11-22 00:05` 结束，计入 **11-21**；耗时仍按真实起止计算，可跨午夜。
- 待办按日终存量：`11-21 23:50` 导入的版本，在 `11-21` 日终计入待办；`11-22 00:10` 发布后，`11-22` 日终不再计入。

### 3.3 当天未结束

| 指标 | 当天未结束时的返回 | 展示 |
| --- | --- | --- |
| `newDrafts` | 截至 `generatedAt` 的暂计数 | “截至 HH:mm，今日尚未结算” |
| `reviewsCompleted` | 截至 `generatedAt` 的暂计数 | 同上 |
| `pendingAtEndOfDay` | `null` | “今日尚未结算” |
| 运行 `total/succeeded/failed/unfinished` | 截至 `generatedAt` 的暂计数 | 同上；`unfinished` 含仍在运行 |
| 运行 `duration` | 仅已结束且可信的样本 | 注明样本数 |

**M3 建议**：当天未结束的“已完成/新增”可以返回暂计数，但必须带 `dayOpen=true`，不能伪装成已结算日；`pendingAtEndOfDay` 必须 `null`。如果 M1/M2 认为暂计数也会误导，可以整日返回 `null`，但不得返回 0。两种方案需 M2 确认展示。

### 3.4 采集前历史

- `reviewsCompleted`：`T0` 之前一律 `null` + `reason=LEGACY_EVENTS_NOT_AUDITABLE`，**不返回 0**。历史发布没有操作者，不能算“人工审核完成”。
- `pendingAtEndOfDay`：`T0` 之前可用基线与 `imported_at` 回放，标 `partial`；若某版本 `legacy_source='unknown'` 且该日结果依赖它，返回 `null` + `reason=LEGACY_PUBLISH_TIME_UNKNOWN`。
- `newDrafts`：`imported_at` 历史可读，通常可算；覆盖起点由 M1 给出，缺失起点标 `partial`。
- 运行趋势：`T0` 之前只有“保存过成功结果”的记录，失败/未完成没有完整记录；`total`/`succeeded` 只能算“已记录数”并标 `partial`，`failed`/`unfinished` 标 `not_collected`，耗时标 `not_collected`。**不能据此说历史失败率为 0 或成功率为 100%。**

### 3.5 缺测与真实零

| 情形 | 返回 | 页面 |
| --- | --- | --- |
| 采集已开启，当天确实没有新草稿/审核/运行 | `0` | “0” |
| 采集未开启/未部署 | `null`，`availability=not_collected` | “未采集” |
| 采集中途开启，只覆盖部分时段 | 有值的计数，`availability=partial` | “部分覆盖，自 HH:mm 起” |
| 当天未结束的日终待办 | `null` | “尚未结算” |
| 历史事件不可追溯 | `null` + reason | “历史不可追溯” |
| 查询失败 | 非 2xx 错误 | 错误态，不返回全零 |

**覆盖状态按指标返回，不按整行共用一个值。** 上线当天可能同时出现：`newDrafts` 用 `imported_at` 可覆盖全天（`precise`）、`reviewsCompleted` 只覆盖 `T0` 后（`partial`，注明起点）、`pendingAtEndOfDay` 的日终快照在 `T0` 后可由基线回放（`precise`）、运行只覆盖 `T0` 后（`partial`，注明起点）。页面与接口必须逐指标标注，不能用最乐观或最保守的一个状态代替全部。

## 4. 系统运行趋势

### 4.1 指标定义

| 指标 | 定义 |
| --- | --- |
| `total` | 当天**实际开始**的 `assessment_run` 数；同一 `runId` 只计一次 |
| `succeeded` | 终态为成功、且规则结果/报告可读的运行 |
| `failed` | 终态为失败、没有完整结果的运行 |
| `unfinished` | 查询时仍未终态的运行：`queued`、`running`、崩溃后恢复核查为 `interrupted` 的记录；**不算失败，也不算成功** |
| `durationSampleCount` | 有可信 `startedAt`/`finishedAt`、`finishedAt > startedAt`、已结束的运行数 |
| `avgDurationMs` | 上述样本的端到端耗时平均值；无样本时 `null` |

- 首版以 `assessment_run` 为范围；模型调用趋势不列为首版强制指标。
- `total = succeeded + failed + unfinished` **只在三者都可用时成立**；采集前历史可能不成立，响应必须带覆盖说明，不能强行配平。
- 缓存命中仍产生新 run，按真实运行计；解释降级但规则结果正常返回算 `succeeded`，可另标“降级”，不伪装成失败。
- 鉴权失败、参数校验失败等**在建立 run 之前**被拒绝的请求不属于本指标；未建立 run 的请求没有 `runId`，不能计入 total。
- 运行中断恢复：只有同时满足“超过运行上限、锁未被持有、原连接已断开”才可置 `interrupted`；不能把仍在运行的任务误标。
- `failed`/`unfinished` 的运行不能序列化成完整报告；API-12/13 应返回明确未完成错误，而不是 500。

> **2026-11-12 核实（E1 #61）：** 正式契约 `1.1.0-rc.1` 的 `RunStatus` 已包含 `queued/running/succeeded/failed`，并写明 E1 不产生 `interrupted`；但当前 `save_run()` 仍只在成功时插入 `status='succeeded'`，代码中没有 `queued` 写入路径。枚举存在不等于运行生命周期已采集：趋势接口不能因为契约有 `queued` 就把未实现的状态当作已记录；`queued` 是否实际落行、API-12 对未完成 run 的稳定错误码，仍待 M1 确认（见 §8.1 第 5 项）。

### 4.2 归日与状态更新

- 按 `startedAt` 归日；若契约只有 `created_at`，首版以 `created_at` 作为开始时间，但 M1 应在生命周期采集中补明确的 `startedAt`。
- 一个运行在 `11-21 23:55` 开始、`11-22 00:05` 成功：计入 `11-21` 的 `succeeded`，耗时 10 分钟；不计入 `11-22` 的 total。
- **跨午夜且当天未结束的运行**：在 `11-21` 日终时它是 `unfinished`；次日后完成后，`11-21` 的该日结果会从 `unfinished` 变为 `succeeded`。这是“按开始日归日 + 结果在查询时更新”的口径，响应必须带 `generatedAt`，页面说明“近期日期可能随运行完成更新”。
- 如果业务希望“日终快照后不再变化”，则跨午夜运行会在开始日永久计为未完成，反而误导；M3 不建议。该选择需 M1/M2/M3 确认。
- 已结束且超过最大运行上限的日期，结果稳定；近期日期可重算。

### 4.3 耗时

- 只纳入可信起止时间：`finishedAt` 存在、`finishedAt > startedAt`、非负差值。
- 旧 `save_run` 在成功时把 `created_at` 与 `finished_at` 写成同值；这些记录**不是 0ms**，而是“未采集耗时”，必须排除出样本，保留原记录并显示覆盖边界。
- 不得把各 `trace_step.elapsedMs` 相加冒充端到端耗时；轨迹耗时是步骤级，可能缺失、重复或跨步骤。
- 平均耗时 = 样本耗时之和 ÷ `durationSampleCount`；没有样本返回 `null`，不返回 0。

### 4.4 不应由历史占位数据推断的内容

- 不能从旧“成功”记录推断历史失败率为 0。
- 不能从 `created_at = finished_at` 推断耗时为 0ms。
- 不能从旧 run 数量推断历史总量完整；旧系统只在成功保存时插入记录，失败/未完成可能没有行。
- 不能从模型调用日志缺失推断“没有调用”或“调用免费”；日志不是结构化事件。
- 不能用 demo/演示数据填充趋势图；样例图必须标“合成数据”。

## 5. `baseline` 的边界

- `baseline` 只用于建立上线时刻 `T0` 的状态基线：在同一事务内锁定 `policy_version`、为当时 `published` 的版本写 `actor_kind='baseline'`、`review_revision=0` 的事件，并写 `collection_baseline`。
- **基线事件不是可追溯的人工审核完成事件**：`actor_user_id` 为 `NULL`，只证明“`T0` 时已发布”，不证明何时、由谁审核。**不计入 `reviewsCompleted`。**
- `occurred_at` 取值：
  - `reviewed_at` 非空 → 用 `reviewed_at`，`legacy_source='reviewed_at'`（近似，不是事件）；
  - `reviewed_at` 为空 → 用 `T0`，`legacy_source='unknown'`（只声明 `T0` 时已发布）。
- **任何情况下都不拿 `imported_at` 顶替发布时间**。
- 基线只解决“待办存量”的起点，不解决历史审核完成数；历史无法还原时标缺测或部分覆盖。
- 运行趋势不适用审核基线；运行生命周期的覆盖起点是 M1 部署采集的时点，历史失败/未完成不能回填。

## 7. 展示含义（M2 复核）

### 7.1 审核工作量

- 标题写“审核工作量”，不要写“审核效率”或“审核通过率”；数据只支持数量，不支持绩效评价。
- “审核完成”文案建议写“审核发布完成数”，并加说明：“以可追溯的审核员发布事件为准；上线前历史不具可追溯操作者，显示为不可追溯。”
- 三个指标分别标 `availability`；不能因为 `newDrafts` 可读，就让用户以为 `pendingAtEndOfDay` 也可读。
- `pendingAtEndOfDay` 是存量，不是当天新增；图注写明“日终未发布版本存量，不含候选”。
- 基线日期用不同底纹/标记，并注明“上线基线，不计入审核完成”。

### 7.2 系统运行趋势

- 成功/失败/未完成三色或三纹理，不能只靠颜色；`unfinished` 不能并进 `failed`。
- 耗时图必须显示样本数；没有样本显示“无可用耗时样本”，不画 0ms。
- 历史覆盖不足时，在图上标“部分覆盖/未采集”，不要用虚线或 0 填充成完整曲线。
- 缓存、解释降级可以作为附注，不改变成功/失败计数；不要另造第五种状态。
- 运行图不展示模型调用次数/费用；首版未落库。
