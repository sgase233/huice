# 评测报告草稿：单智能体基线 vs 多阶段方案（M1，2026-11-06）

> **归属**：分工表把「锁定评测报告」放在 11/15 与 M3 的名下；这份是 M1 侧的跑数与结论草稿，数值、失败样例与局限可直接搬进终稿。11/12 的验收要求是「所有 P0 场景通过，失败样例和指标写进评测报告」，本文对应其中「指标」与「失败样例」两段。
>
> **可复现性**：所有数字均由 `services/api/app/ablation/` 的五条子命令产出，输入文件哈希写在每个 JSONL 的表头（两份跑数文件 `same_input=true`）。分支 `m1/ablation-baseline`，提交 `7bd0941`。

## 1. 结论

1. **给同一个模型同样的输，它会读错事实、也会说反**：单智能体基线在 146 条标注上做到 87.0%，但 11 条硬门槛里有 **2 条**把「不满足」判成「满足」——其中一条的理由里自己写着「研发费用 30 万元低于 100 万元」，结论却仍是 `satisfied`。
2. **时效判断是基线的稳定短板**：12 条已过适用期的 case 中漏了 6 条，全部是同一政策（适用期至 2026-09-08），判断日 2026-11-06 早已过期，模型仍写「尚未到期」。
3. **现方案的四态一致率 100%，但这个数不能读成「更准」**：现方案的条件与规则本身就是标注所依据的那一套，同行比较是循环的。有信息量的差别在**成本与可控性**：现方案 0 token 边际成本、过期标记由代码算而不是由模型说。
4. **抽取阶段是目前最弱的一环**：冷启动抽取对已仲裁条件的覆盖只有 32%–40%（三轮），也就是「没给条件清单时会漏掉六成」。而它此前是 **0%**，原因是提示词没写清楚表达式键名，与模型能力无关。
5. **一轮基线 + 四轮抽取合计 0.7741 元**（官方价目、高峰时段、按缓存未命中上限计）。

## 4. 失败样例

### 4.1 硬门槛误判（唯一会直接导致错误申报建议的一类）

**① C017/SRDI-002｜标注 `not_satisfied`，基线 `satisfied`**

条件是三项同时成立，第一项就不过：

```
rdExpense(2024) ≥ 1,000,000 元        事实：300,000 元      ✗
rdExpenseRevenueRatio(2024) ≥ 3%      事实：6%              ✓
revenue ≥ 1000 万 或（revenue ≤ 1000 万 且 equityFinancing ≥ 2000 万）
```

模型给的理由原文：

> 「上年度研发费用 30 万元低于 100 万元，但研发费用占营收比 6% 和营业收入 500 万元，且有股权融资 0 元，**不满足融资条件**」

**理由里已经承认不满足，结论仍然写成 `satisfied`。** 这类错误不是「算错数」，而是「说一套判一套」——单次调用没有中间步骤可以核对，也就没有任何东西能拦住它。

**② C024/RDSUB-001｜标注 `not_satisfied`，基线 `satisfied`**

条件之一是 `creditRecord == true`（未被列入经营异常名录或严重失信名单），企业事实是 `creditRecord = false`。模型写：

> 「注册 2018 年满两会计年度，2024、2025 均享加计扣除，2025 年研发费用增量 200 万元达标，**诚信记录良好**」

把一个 `false` 读成了「良好」。同样是一条事实读错就翻盘。

### 4.2 时效识别（6 条全漏）

12 条已过适用期的 case 中，C025–C030 六条全部漏判，且都来自 `SZ-GRANT-HIGHTECH-2021`（适用期至 **2026-09-08**，判断日 2026-11-06）。模型的理由分别写着：

> C025「政策适用期至 2026-09-08，**尚未到期**」
> C026「适用期至 2026-09-08，**未过期**」
> C029「适用期 2021-09-08 至 2026-09-08，**判断日未超期**」

日期比较方向错了两个月。现方案这 12 条全对，因为过期与否是 `versioning.resolve_validity` 算的，不经过模型。

对照另一半：另外 6 条（C013–C018，`SZ-GRANT-SRDI-2025`，生效至 **2025-11-10**）基线全部答对。所以这不是「日期方向一律搞反」，而是**日期判断没有稳定的判据**——同一次运行里，早一年的判对了、晚两个月的判错了，两次都对同一个事实做比较，结果不一致。一次运行不足以判断这是系统性偏差还是抽样波动——要区分，得把同一条 case 重复跑几轮；本报告只做到如实记下两边相反的结果。

### 4.3 另一方向：把算对的说成算错

- **C003/SME-004**：季度平均值 (625+675+725+775)/4 = 700 万元，远低于 5000 万元，基线判 `not_satisfied`。它的理由是「700 万元，**超过** 5000 万元？——实为 700 万元，未超 5000 万元，满足。」——自问自答之后结论仍与自己的推理相反。
- **C002/SME-004**：四季度平均 1000 万元，同样判成 `not_satisfied`。

这类「过度严格」的错误在业务上同样有害：本可申报的企业被判不满足，企业就该放弃申报。

## 5. 冷启动抽取（现方案独有的阶段）

| 轮次 | 产出条款 | 收下 | 引文不实 | 对已仲裁条件的覆盖 |
| --- | --- | --- | --- | --- |
| 修补前提示词 | 41 | **0** | 2 | **0%** |
| 第 1 轮 | 20 | 17 | 1 | 32% |
| 第 2 轮 | 22 | 15 | 1 | 36% |
| 第 3 轮 | 27 | 22 | 1 | 40% |

**修补前的 0% 不是模型的问题。** 旧提示词只写「expression 只能是 and/or/compare…」，从没说过算子写在 `op` 键、`and/or` 的子项在 `children`、`compare` 还要 `period` 与 `comparator`。契约是 `additionalProperties: false`，键名靠猜必错——模型于是自己起了 `type` 与 `conditions`，41 条全部被判「算子不在契约词典内」丢弃。修补后逐算子列出键集合、样例由结构体序列化，覆盖率升到 32%–40%。

**覆盖率是下限**：只有抽取结果的引文包含标注原文片段才算命中，抽到同一条件但引文取短了也记未命中。三轮 32/36/40 的差异来自模型自身的抽样，说明**单轮数字不能当结论**，报告只能写区间。

**幻觉条款率**：三轮各 1 条引文在正文中找不到，分母分别是 20/22/27 → 5.0% / 4.5% / 3.7%。基线没有抽取阶段，这个指标对它不适用；对应的「等价物」是无依据断言率，基线为 0。

## 7. 局限（写进报告而不是藏起来）

1. **现方案的 100% 是循环的**：标注结论与现方案用的是同一套条件与规则，同行比较没有信息量。本次能比较的其实是「有已仲裁条件 + 确定性规则」与「只有一个模型」的差别；不能声称现方案「判断更准」。
2. **基线拿得到条件清单**（代号 + 原文片段），否则对不上 `criterionId`。这是**对基线有利**的取舍：真实场景里模型要自己从正文里找条件，那部分难度被移到了抽取阶段单独度量。
3. **硬门槛只有 11 条**，2 条误判的 95% 区间是 5%–48%，不能说「误判率 18%」以外的任何精确断言。
4. **时效分母只有 12 条**，且 12 条来自 2 个政策；6 条全错说明的是「模型会算错日期」，不能推广成「模型对时效判断的整体错误率是 50%」。
5. **抽取覆盖率是下限**（引文包含才算命中），且**单轮波动大**（32%–40%），不能报单点。
6. **费用按缓存未命中价计**，是上限；客户端没有记录缓存命中 token 的能力，无法给出精确账单数。
7. **灌库时三个「先执行、后发文」版本的发布日被压到生效日**，只为满足 `policy_version_dates` 的 `effective_from >= published_at`；改的是临时库，不是 CSV。这与真实政策有出入，但只影响灌库，不影响指标。
8. **`applicable_entities` 登记表没有这一列**，灌库时统一填「企业」占位；它只进政策详情与准备清单模板，不参与条件求值，对本报告的数字无影响。
9. **每个方案只跑了一轮**（基线），模型非确定性未做重复实验度量；抽取那部分跑了三轮，用于估计波动。
10. **人工复核尚未执行**：`review.csv` 已生成 60 行（每方案 30 条，`not_satisfied` 各 7/6 条，种子 20261106），复核结论与耗时两列留空，需要一个复核人填写。复核结果如果是「模型判得对、标注错」，上面的数字会变。

## 8. 复现

```bash
cd services/api
export MODEL_MODE=deepseek            # 需要 DEEPSEEK_BASE_URL / DEEPSEEK_MODEL / DEEPSEEK_API_KEY
python -m app.ablation baseline    --out runs/baseline.jsonl
python -m app.ablation extraction  --out runs/extraction.jsonl
python -m app.ablation pipeline    --dsn "$HUICE_EVAL_DATABASE_URL" --out runs/pipeline.jsonl
python -m app.ablation metrics     --baseline runs/baseline.jsonl --pipeline runs/pipeline.jsonl
python -m app.ablation review-sheet --baseline runs/baseline.jsonl --pipeline runs/pipeline.jsonl --out runs/review.csv
```

`pipeline` 会在目标库里建临时 schema、跑两遍全部迁移、结束时删掉；库地址只认 `HUICE_EVAL_DATABASE_URL`（或 `--dsn`），与服务端 `DATABASE_URL` 相同会被拒绝。`asOf` 默认取运行当天的北京时间正午，比对本报告的数字时要显式传 `--as-of 2026-11-06`，否则时效相关的三行都会变。
