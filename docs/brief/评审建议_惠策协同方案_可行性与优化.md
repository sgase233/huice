## 0. 一句话结论

**方案能做完，且完成度、边界意识、评测意识都明显高于同龄团队；真正的风险不在"做不出来"，而在"做出来之后不像华为 ICT 创新赛的作品"。**

赛题要求明确是**双轴评分**：

- **轴 A**：AI 应用本身的价值、创新性与完成度 —— 你的方案在这里已经很强；
- **轴 B**：如何用华为云产品（CodeArts / Skills / RDS / Redis / MaaS）把想法变成应用 —— 你的方案在这里**几乎是空白**。

轴 B 是赛题文字里反复强调的东西，不做等于主动丢分。本文件的核心建议就是**把轴 B 补齐，同时把轴 A 的技术尖点做深**。

## 1. 两条重要判断修正

策划案中若干表述是在赛题细则未知时写的，现已有官方口径，需要修正：

### 修正 1：CodeArts 不是"辅助工具"，是必选的展示内容

原策划案 §5：

> "使用华为云码道 CodeArts 代码智能体辅助需求拆解、编码、调试和可复现测试，并记录实际使用截图及开发日志。"

**这一句远远不够。** 赛题要求是：

> "应体现华为云产品在**需求理解、代码生成、项目构建、问题修复、部署上线**等环节的使用价值，鼓励形成'想法到应用'的高效开发实践。"

也就是说，CodeArts 的使用过程**本身就是作品的一部分**，需要被系统采集、结构化呈现、写进演示视频。不能事后补截图。

### 修正 2：技术选型已可定稿，不要再写"待选型"

原策划案 §5：

> "模型推理、计算、存储与检索资源在开工时根据赛题细则、账号权限和预算做最终选型"

赛题已给出明确路径：**华为云代金券购买 MaaS 等云资源调用大模型能力**；任务要求明确点名 **RDS、Redis**。因此：

- 模型走 **MaaS**，不再讨论"用不用盘古/昇腾"这类开放式问题；
- **RDS + Redis 是赛题点名的必做项**，不能继续用"关系数据库"这种模糊表述；
- 昇腾推理**不是硬性要求**，不必为国产化叙事强行上，把精力放在可交付性上。

## 3. 技术栈定稿建议

| 层 | 建议选型 | 理由 |
| --- | --- | --- |
| 开发工具 | CodeArts 代码智能体 + AI 开发者空间 | 必选 + 官方资源 |
| 模型服务 | **华为云 MaaS**（按可用清单选，优先盘古，退路 DeepSeek / Qwen） | 代金券可购买，赛题认可路径 |
| 主数据库 | **RDS for PostgreSQL** | 政策版本、规则 AST、画像、任务；JSONB 存规则表达式非常合适 |
| 向量检索 | **RDS pgvector**（首选）；CSS 作为时间富余时的增强 | 少一个服务少一份运维负担；CSS 是加分项而非必需项 |
| 缓存 / 队列 | **Redis**（必须有实质用途，见下） | 赛题点名 |
| 对象存储 | OBS | 政策原文 PDF、附件、用户上传材料 |

### 3.1 Redis 的"名正言顺"用法

不要为了"用了 Redis"而用。建议把缓存键设计和"结论时效性"这个创新点咬合：

```
assessment:{enterprise_id}:{policy_id}:{policy_version}:{fact_hash}
```

政策修订或企业画像变化 → 版本号 / 事实哈希变化 → 键自然失效 → 触发重算。

**这一句在答辩中价值很高**：同时回答了"为什么用 Redis"和"版本感知创新怎么落地"。

其他合理用途：

- 政策原文解析结果缓存（避免重复调用大模型，直接省钱）；
- 异步解析任务队列（采集 → 解析 → 人工抽检的解耦）；
- 接口限流、会话草稿。

### 3.2 MaaS 成本控制（务必提前算）

条款抽取是 token 消耗大户，代金券额度有限。策略：

1. **离线批处理完成抽取**，解析结果落 RDS 后不重算，演示时只做匹配与解释；
2. 小模型初筛 + 大模型处理难例；
3. 抽取结果与原文入库，演示当天不做大规模实时推理，避免被限流。

## 5. 三个能实质提升技术含金量的改造

现有方案的技术内核是"RAG + 规则引擎"，属于成熟范式，创新分拿不满。以下三项成本可控、答辩效果显著：

### 5.1 条件 DSL + 引用校验双通道（必做）

把数据模型中的 `Criterion`（条件类型、运算符、值）升级为**可解释的表达式 AST**，支持：

- 区间判断（应纳税所得额 ≤ 300 万）
- 比例、期间平均值（年度季度平均从业人数）
- 复合逻辑（AND / OR / NOT）
- 行业负面清单（排除项）
- 时点条件（成立时间、政策生效时点）

**关键工程点**：抽取器输出规则后，再用一个**独立的校验器**验证"规则中的数值与条件确实出现在所引用的原文片段中"。这是对大模型幻觉的直接工程对抗，且可量化（引用忠实度）。

> 这一块应从 §4 表格里的一行，提升为**技术方案的主体**——它才是这个项目最难、最有价值的部分。

### 5.2 把"最少量的补充问题"做成算法（强烈推荐）

现有描述：

> "不能判定时向用户提出最少量的补充问题。"

可以升级为真正的方法论贡献：**用信息增益 / 决策树思想，选择最能区分四态结论的下一个问题**，形式化为最小提问集（set cover）。

演示效果极强：同一家企业，随机提问需要 8 个问题，算法只需 3 个问题就锁定结论。**可视觉化、可对比、有算法内核**，而且同类产品几乎没人这么做。

### 5.3 结论的时效性建模

给每个 `Assessment` 增加**结论有效期区间**（不是政策有效期，而是"这个判断在什么条件下仍然成立"）。政策版本变更或企业事实变更时，自动标记"失效待复核"。

把"版本感知"从一句宣传语变成**数据结构**，配合 3.1 的 Redis 键设计，形成完整闭环。

## 6. "多智能体"需要一次消融实验来支撑

五个 Agent 的分工表写得漂亮，但评委能看出本质是一条 pipeline，拆成五个函数也成立。若被问"为什么不用一个 Agent 加几个工具"，现有文档答不上来。

两个补救方向，建议都做：

1. **给出必要性论证**：不同角色上下文不同、工具不同、失败模式不同，需要在特定节点插入人工复核，且需要独立评测每个环节。定位为**职责分离**而非"多智能体更先进"，姿态放低反而加分。
2. **做消融实验**：同一批样例，跑"单 Agent 端到端" vs "多 Agent + 规则引擎"，对比条款抽取准确率、幻觉率、人工复核耗时。

> 这一个实验就能把"多智能体"从噱头变成论据，而且是评委最喜欢的"有对比、有数据"。

## 7. 评测方法学的修正（最易被专业评委击穿）

| 问题 | 现状 | 修正建议 |
| --- | --- | --- |
| **样例数对不上** | MVP 为 2 项国家级税收政策 + 3—5 项地方通知（共 5—7 项），演示企业"至少 3 家"，3 × 7 = 21 条，**达不到 §7.3 要求的 30 条** | 扩到 6—8 家合成企业，或增加政策条目 |
| **缺标注者间一致性** | 直接宣称"与双人共识一致率 ≥90%" | 先报告 Cohen's κ，再报告系统相对共识的准确率，并说明分歧仲裁规则。若 κ 仅 0.7，"90%"这个数字没有意义 |
| **"硬门槛误判为适用 0 例"不可信** | 30 条样本上 0 错误 | 在**留出集**上报告，给出误判数与置信区间，并主动展示失败样例 |
| **指标粒度错误** | 以"政策"为单位判对错 | 补充**条件级**指标：条款抽取 precision / recall、引用忠实度、幻觉条款率、过期识别率、人工复核节省时间 |
| **"原文定位覆盖率 100%"不是指标** | — | 这是设计约束（强制每条规则绑定 span 必然 100%），写进去反而显得不懂评测 |

### 7.1 建议替换后的指标表

- 条件抽取：precision / recall（条件级）
- 引用忠实度：结论所引片段是否真正支持该结论（100 条抽样人工核验）
- 硬门槛误判：留出集上的误判数 + 95% 置信区间
- 四态判断：与双人共识一致率 + 标注者间 κ
- 过期事项识别率
- 单企业端到端耗时（**需明确是否含人工复核环节**；3 分钟若指机器时间，应注明）
- 消融对比：单 Agent vs 多 Agent
- 基线对比：人工检索 / 关键词搜索 / 通用问答（现有方案已有此设计，保留并强化）

## 8. 差异化叙事需要更锋利

§6 的竞品分析很诚实，但诚实过头会变成自我否定：深 i 企在深圳做政策匹配 + 资助测算 + 推送，本项目试点也在深圳。评委一句"这不是已经有现成的了吗"就能打穿。

建议把楔子收窄成**公共平台结构上不会做**的三件事：

1. **跨层级统一视图**：国家税收优惠 + 地方资金项目同表呈现，但分两条流程处理（现有方案已写对，是最强的点）；
2. **企业侧证据管理**：政府平台知道你符不符合，但不知道你内部缺哪份材料、谁负责、什么时候交；
3. **结论的时效性**：政策修订后哪些旧结论失效、报告如何保留当时依据——**几乎没有产品正面解决"结论会过期"**，这比"精准匹配"新得多。

反向原则：主动放弃"我们比深 i 企更准"这类宣称，定位为**互补层**（甚至潜在合作方）。

## 10. 范围裁剪与交付物

### 10.1 该砍的

§3.1 与 §4 的产品面铺得过大：责任人协作、任务状态流转、多角色权限、监控告警。

**创新赛的评分重心是 AI 技术与演示效果，不是 CRUD 完整度。**

- **砍掉**：责任人协作、任务状态机、多角色权限（演示版做成静态清单即可）
- **保留并加强**：条款结构化、四态判断、证据缺口、版本重算、可审计 trace
- 省下的时间投入**评测集质量**与**演示脚本打磨**，边际收益高得多

### 10.2 交付物清单（建议写入策划案）


## 11. 演示需要一个"反转时刻"

"录入企业 → 看到匹配列表"是这类项目的通用演示，评委看多了会走神。建议设计一个 30 秒反转：

> 一家看起来完全符合条件的企业，系统判定"不满足"，镜头拉到那条被忽略的**行业排除条款**；
> 或者：现场改掉某条政策的生效日期，系统立刻把两条结论标红为"依据已失效"，并指出是哪一条条款变了。

这个瞬间同时证明四态判断、证据定位、版本感知三件事，比讲十分钟架构有效。

**建议把 "政策修订导致结论重算" 从补充环节前置为演示主线。**

### 11.1 演示结构建议（按赛题要求调整排序）

1. **30 秒痛点**
2. **1 分钟华为云开发过程**（CodeArts → Skills 开通 RDS/Redis → 部署录屏）← **前置，因为是赛题核心要求**
3. **2 分钟产品演示**（含反转时刻）
4. **1 分钟技术架构**（DSL、校验器、多智能体 trace）
5. **1 分钟可信度**（评测指标 + 失败样例）
6. **结尾**：单城试点 → 多地区复制的机制

## 12. 开工前必须 de-risk 的 4 件事

## 13. 排期隐患

条款标注是关键路径，且是最耗时的环节（一条政策拆成 10—20 个条件，还要双人复核）。现有排期把它放在"需求与规则冻结"阶段，但它会直接卡住 11 月的评测。

- **第 1 周并行开始标注**，不等 MVP 完成；
- 10/25 的"规则冻结"要真正冻结——**冻结的是政策清单与条件 schema**，之后只加数据不改结构；
- 11/15 之后原则上不加功能，只做评测与演示打磨；
- CodeArts 证据采集是**贯穿全程**的日常动作，不是某阶段任务。

## 15. 验证路径的务实建议

原方案计划"邀请 5 家左右目标企业试用"。对学生团队而言，一个月内触达 5 家中小企业难度较大。

**更可行的路径：找 1 家代理记账公司或孵化器 / 产业园区。**

- 他们每天就在做这件事，能提供真实痛点、真实样例、真实评价；
- 一个联系人即可覆盖几十家企业的场景；
- 答辩时更容易讲出可信的"真实用户反馈"；
- 也天然是潜在的合作 / 分发渠道。

若确实无法触达，如实报告合成样本结果即可——现有方案已具备这个诚实姿态，保持。

## 16. 评审视角的一句话提醒

标题是"**基于华为云产品打造** AI 创新应用"——"**打造**"两个字是题眼。

不是交一个跑在云上的应用，而是**证明你用华为云把东西造出来了，而且造得快**。

原方案在"应用好不好"这条轴上已超过大多数队伍，但在"怎么造出来的"这条轴上几乎是零分。补上这一块的成本很低（记录习惯 + 一节文档 + 一段录屏），却是这份赛题里性价比最高的一块分数。
