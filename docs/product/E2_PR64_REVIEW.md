## 1. 结论

**M3 不签收 E2，也不把 DISC-AT-01—07 任何一项写成“通过”。**

M2 在 `70e00d5` 上已确认没有新的明确代码阻塞；M1 对并发幂等、正文失败状态、预算预留、附件提示持久化等问题的修复有效。但 M3 从政策事实、业务口径和验收角度仍有两个 P1 业务阻塞：

1. **附件依赖来源无法形成可引用、可发布的草稿。** S03、S04、S05 的资格条件/标准/窗口至少一部分只在附件中；系统只保存附件 URL，不下载、不解析，也不把附件作为草稿来源。审核员按提示“人工补录”附件条件时，引文不在正文中，会被引用校验拦住；没有附件来源，无法建立合法引用。
2. **换 URL 同内容的判重按当前实现很可能失效。** 2026-11-12 按仓库同款 `html_to_text`/`normalize_text` 算法复现，S01 与 S10 虽含同一关键句，但整页规范化文本长度分别为 1,976 / 1,258 字符，SHA-256 不同；`runner.py` 只按 `content_hash` 精确匹配判重，因此 S01/S10 会被当成两条新候选。DISC-AT-04 的“换 URL 同内容”不能成立。

**附件是否本轮必做：** 全平台、全格式的附件自动获取/抽取/引用不必作为 E2 后端合并的绝对前置；但对首批样本中的 S03/S05（以及 S04 的附件标准），如果要算作 E2“已支持”，附件链路就是必做。若本轮不做，必须明确把这些来源排除出 E2 自动发现验收范围，不能靠一条无法解除的提示替代。

**是否阻断发布：** 当前不应简单把 `ATTACHMENT_NOT_EXTRACTED` 加入发布阻断集合——它现在会被永久保留且没有解除机制，直接阻断会导致所有带附件政策永远无法发布。正确口径是：先补“逐附件可追溯核对/处置”记录，再把未处置附件作为发布阻断；在该机制补齐前，附件型来源不纳入 E2 可发布/可验收范围。当前系统没有这种可追溯确认，“审核员口头核对后发布”不能算已有功能。

**未执行证据：** 真实抓取器、真实模型、云端部署、010 迁移、三方联合验收均无证据，不能写“通过”。

## 3. 具体问题（按严重程度）

### P1-1 附件条件无法建立引用，提示“人工补录”与实际能力矛盾

**位置：**
- DISC-07 提交只建正文来源：[`discovery.py:343`](../../services/api/app/routes/discovery.py#L343)
- 所有引用片段被强制改挂到 `draft.sources[0]`（正文）：[`discovery.py:831`](../../services/api/app/routes/discovery.py#L831)
- 抽取只读取 `kind=body`：[`agents/extraction.py:280`](../../services/api/app/agents/extraction.py#L280)
- 附件提示文案要求“条件若写在附件里，请在保存条件时人工补录”：[`discovery.py:528`](../../services/api/app/routes/discovery.py#L528)
- 发布只拦条件级 findings 或 `POLICY_BLOCKING_CODES`：[`admin_policies.py:403`](../../services/api/app/routes/admin_policies.py#L403)

**触发场景：** S03 的申报窗口/分批要求、S04 的认定标准/知识产权指标、S05 的资助标准/条件位于附件；审核员按提示在 DISC-06 或 API-06 补录附件条件。

**影响：**
- 引文摘自附件 → 不在正文中 → `SPAN_QUOTE_NOT_FOUND`；无引文 → `CRITERION_NO_SPANS`；发布被 422 拦住。
- 系统没有“把附件作为 `policy_source(kind=attachment)`”的候选接口，所以审核员无法在候选链路里完成合法补录。
- 审核员若只录入正文能支持的条件，可能把不完整的政策发布出去；这正是附件提示要防止的情况，但当前提示无法解除。
- 该问题直接使 S03/S04/S05 无法在 E2 候选链路中形成完整、可发布的草稿。

**建议：** 二选一，不能含糊：
- **A. 补最小附件来源链路**：允许把附件文本作为 `policy_source(kind=attachment)` 存入草稿，引用校验覆盖全部 sources；附件获取做 SSRF/类型/大小防护；DOC/DOCX/ZIP 需安全解包或离线转换；模型抽取可以仍只读正文，人工补录条件必须能引用附件。
- **B. 本轮明确排除附件依赖来源**：S03/S04/S05 不纳入 E2 自动发现验收，继续走人工路径；同时写明人工导入目前只接受 PDF/UTF-8 文本，DOC/DOCX/ZIP 需离线转换。

### P1-2 换 URL 同内容判重按当前实现很可能失效（DISC-AT-04）

**位置：**
- `content_hash` 只对整页规范化文本做 SHA-256：[`runner.py:307`](../../services/api/app/discovery/runner.py#L307)
- 判重只做 `content_hash` 精确匹配：[`runner.py:309`](../../services/api/app/discovery/runner.py#L309)
- `html_to_text` 保留整页可见文本（导航、页脚、面包屑都在内），只做空白折叠：[`fetch.py:514`](../../services/api/app/discovery/fetch.py#L514)

**实测（2026-11-12，按仓库同款算法复现）：**
- S01：27,618B，规范化文本 1,976 字符，SHA-256 `e1c0417a…`。
- S10：27,492B，规范化文本 1,258 字符，SHA-256 `e8dc92cc…`。
- 两页都含“财政部 税务总局公告2023年第7号”和“再按照实际发生额的100%在税前加计扣除”，但整页文本哈希不同。
- 按 `runner.py` 的精确哈希匹配，S01/S10 不会判重，会生成两条候选。

**影响：** DISC-AT-04 的“换 URL 同内容”不成立；跨站转载会被当成新政策，审核端重复推荐。现有测试只覆盖“同 URL 同内容第二轮判重”，没有覆盖换 URL 同内容。

**建议：** 判重前抽取正文容器（去掉导航/页脚/面包屑），或用“文号 + 标题 + 关键正文规范化”组合键；补 S01/S10 的真实页面 fixture 用例，并断言二者只产生一条候选。不能只用原始 HTML 哈希，也不能假设“关键句相同就等于整页文本相同”。

### P1-3 首批 D/F 根页会被当成单篇正文，产出伪候选

**位置：** `if not links: links = [canonicalize_url(page.url) or page.url]`：[`runner.py:259`](../../services/api/app/discovery/runner.py#L259)

**实测（2026-11-12）：**
- D 组 `https://www.sz.gov.cn/zfgb/`：200，959B，页面链接数 0。
- F 组 `https://www.gov.cn/gongbao/`：200，898B，仅 1 个链接 `currentissue.htm`。
- 两者都是框架/入口页，不是政策正文。按当前逻辑，D 根页会把自己当成单篇正文；F 会把 `currentissue.htm` 当成正文抓取。

**影响：** 生成 `extraction_failed` 伪候选或错误“正文”候选；运行状态可能显示“发现/抽取失败”而不是“栏目不可列取”。DISCOVERY_SOURCES 已把 D/F 标为“疑似框架页、未验证列表”，但代码没有对应防护。

**建议：** 增加 `singleArticle` 显式配置，或至少用标题关键词、最小正文长度、文章链接特征做判别；无链接的框架页应记来源级 `unsupported_list/fetch_failed`，不得当正文候选。首批配置不要直接填 D/F 根页，除非先补这个防护和实测。

### P2-1 附件内容变化不进入判重

`content_hash` 只覆盖正文；`attachment_urls` 不参与哈希或版本判断。若 S03 的申报指南附件在正文 HTML 不变的情况下更新，系统会继续判为“同 URL 同内容”的重复，不提示版本变化。对“关键信息只在附件”的来源，这会直接漏掉政策修订。

**建议：** 附件获取后记录附件内容哈希/大小/类型并纳入版本指纹；未获取前至少在文档和验收中写明“附件变化本轮不可检测”，不能声称覆盖同 URL 内容变化。

### P2-2 人工导入也不能直接读取 DOCX/DOC/ZIP

[`ingestion.py:182`](../../services/api/app/agents/ingestion.py#L182) 的 `_decode_text` 只接受 UTF-8 文本；PDF 单独解析；DOCX/DOC/ZIP 会因二进制被 415 拒绝。因此“回退人工导入”对 S03 ZIP、S04 DOCX、S05 DOC 不是开箱即用，必须先离线转成 PDF/文本。文档应写明这一点。

### P2-3 候选列表没有附件标识

[`schemas.py:723`](../../services/api/app/schemas.py#L723) 的 `CandidateSummary` 没有 `attachmentUrls`/`hasAttachments`/附件 finding。审核员在列表页无法判断哪些候选必须打开附件核对，只能逐条进详情。建议增加 `attachmentCount` 或 `attachmentsPending` 只读字段。

### P2-4 附件 URL 只按域名过滤，允许 http；契约要求 https

[`fetch.py:565`](../../services/api/app/discovery/fetch.py#L565) 的 `find_attachments` 只调用 `_is_official` 检查主机名；`canonicalize_url` 允许 `http`。而 [`openapi.yaml`](../../contracts/openapi.yaml) 的 `OfficialUrl` 要求 `^https://`。如果页面存在 `http://…gov.cn/…pdf`，候选详情会返回不符合契约的 URL。当前不抓取附件，所以不是 SSRF；但契约/生成类型会不一致，未来补附件获取时必须逐跳复检。

### P2-5 多窗口无法表达

[`CandidateMetadata`](../../services/api/app/schemas.py#L701) 只有一个 `applicationWindow`。S03 有两批网络填报和两批书面材料窗口；当前只能填合并区间，容易让时间线误读。首版若不支持多窗口，必须在页面/数据中明确“分两批，区间为合并值”，不能静默压平。

### P2-6 验收证据缺口

- 没有 `version_changed` / 换 URL 同内容的测试；现有测试只覆盖同 URL 第二轮判重。
- 没有“提交与过期竞争”的并发测试。
- 没有配置并发 PUT、30 分钟墙钟超时的测试。
- 没有真实站点抓取、真实模型、云端部署、010 迁移、三方联合验收证据。

### P2-7 文档/注释仍称“附件 PDF 已抽取”

[`fetch.py:27`](../../services/api/app/discovery/fetch.py#L27) 写“附件里的 PDF 会抽取文字”；[`010_policy_discovery.sql:154`](../../infra/sql/010_policy_discovery.sql#L154) 写“PDF 已抽取，其余记在这里”。实际实现是：附件一律不下载、不解析，只记 URL；只有“直接把 PDF 当正文 URL 抓取”时才解析 PDF。这些说明会误导审核员/运维，建议统一改为“附件不获取，只记录 URL”。

## 4. 附件范围与发布口径

### 4.1 附件是否本轮必做

1. **全平台全格式自动附件链路：不必作为本 PR 合并的绝对前置。** #47 已确认的是“提交前抽取结构化条件”，没有明确要求自动解析附件；M1 也说明共享 `agents/extraction.py` 只读正文，改它会牵动 API-04，适合单独 PR。
2. **首批样本范围内：S03/S05 是必做或必须排除。** S03 的申报窗口只在附件 1，S05 的窗口只在 `.doc`，S04 的认定标准/知识产权指标在 DOCX。若这些来源要算 E2 首批“已支持”，没有附件获取/保存/引用就无法完成业务闭环。
3. **当前最小可交付不足。** 现在只有“记录 URL + 持久提示”；缺少“逐附件处置/确认”和“附件作为草稿来源”。因此不能把当前状态描述为“附件已核对/已覆盖”。

**M3 建议：** 本轮优先选 **B（明确排除）**：S03/S04/S05 不纳入 E2 自动发现验收，继续人工路径，并写明 DOC/DOCX/ZIP 需离线转换；若负责人要求这三项进入 E2 演示/验收，则必须做 **A（最小附件链路）**，不能只靠提示。

### 4.2 存在 ATTACHMENT_NOT_EXTRACTED 时是否阻断发布

**不建议现在直接阻断，也不建议现在宣称“核对后可发布”。**

原因：
- 当前这条 finding 由 `attachment_urls` 派生、被 `PRESERVED_SOURCE_FINDING_CODES` 永久保留，没有解除/确认机制。直接加入 `POLICY_BLOCKING_CODES` 会让所有带附件政策永远无法发布。
- 但若完全放行，又没有任何“审核员确实逐份看过附件”的可追溯事实；口头确认不能算系统功能。
- 正确顺序是：先补“逐附件处置”记录，再让未处置附件阻断提交/发布。处置记录至少应包含：

| 需要的可追溯事实 | 当前是否具备 |
|---|---|
| 审核员身份/角色（服务端会话） | 会话存在；但发布 trace 未写附件级确认，不能作为逐附件证据 |
| 确认时间 | 发布 `reviewed_at` 有；附件级确认时间无 |
| 附件 URL | 有（`attachmentUrls`） |
| 附件内容哈希、大小、类型 | 无（未下载） |
| 每个附件的处置结论（无新增条件/已补录/非政策内容） | 无 |
| 从附件补录的条件及其附件引用 | 无（附件不能作为草稿来源） |
| 候选→草稿→发布→附件确认的不可变审计链 | 部分（候选提交关系有；附件确认无） |

**M3 建议口径：**
- 在本轮，附件型来源不进入 E2 自动发现的可发布/可验收集合；如果负责人决定允许人工放行，必须在验收记录中写明这是“系统外人工控制”，不计为 DISC-AT-05 通过。
- 后续补功能时，采用“逐附件 disposition + 未处置即阻断”的模型；不要用一条不可解除的全局 finding 直接阻断。
