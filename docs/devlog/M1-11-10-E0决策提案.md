## D1 鉴权兼容、会话实现与有效期

**结论**

1. **两类旧通道降级为「运维通道」，不再作为业务身份**
   - `ADMIN_TOKEN` Bearer：**保留**，仅用于 `/admin/**` 全部管理端点与 `GET /assessment-runs/{runId}/trace` 的审核视图；**不得**用于企业业务数据的读写，不得进入浏览器、不得作为前端构建变量、不得写进前端配置。
   - `huice_demo_session`：**保留为外层访问门禁 + 只读合成数据**，可以读 6 家无主合成企业和政策库；**不得代表任何用户**，不得访问 `/auth/me`，不得写入任何对象，不得读取任何 `owner_user_id` 非空的数据。
   - 红线：**不能靠「旧 cookie 或新 cookie 任一个有效」放行企业数据**。旧通道只对 `owner_user_id IS NULL` 的对象生效。

2. **会话落 DB，可撤销**
   - 表 `user_session`：`token_hash`（sha256）唯一，明文只进 Cookie，库内与日志内都不出现明文。
   - Cookie `huice_session`：`HttpOnly; Secure; SameSite=Lax; Path=/`；`APP_ENV=local` 时关闭 `Secure`，其余环境必须开启。

3. **有效期**：绝对 **12 小时**（`SESSION_TTL_HOURS`，默认 12）；空闲 **30 分钟**滑动（`SESSION_IDLE_MINUTES`，默认 30），每次请求刷新 `last_seen_at`。两者取先到者。

4. **撤销时机**：登出立即写 `revoked_at`；**改密撤销该账号全部会话**；封禁/停用撤销全部会话；过期会话由定时任务清理。撤销后旧 Cookie 下一次请求即 401。

5. **CSRF**：登录/注册响应返回 `csrfToken`；所有写请求校验 `X-CSRF-Token` 且 Origin 同源，GET 不校验。

6. **限流**：登录/注册按 `IP + username` 5 次/分钟；连续 10 次失败锁 15 分钟。Redis 不可用时**不阻断、记 warning**——演示可用性优先于强限流，这一点接受风险。

7. **角色与账号来源**
   - `enterprise` 必须绑定唯一企业；`reviewer` 的企业字段可空；不设第三角色。
   - 保底管理员是预置 `reviewer`，由部署 CLI 创建，初始密码来自 `ADMIN_INITIAL_PASSWORD`（≥12 位），不进 SQL、不进仓库。
   - 审核员注册走 `REVIEWER_SIGNUP_KEY`（≥32 位、服务端环境变量、可轮换），只在服务端比对；密钥错误与普通校验失败返回同一提示。

8. **归属语义**：企业用户读/写非本人对象一律 **404**（不用 403，不泄露存在性）；审核员全局**只读**业务数据，不修改他人企业事实；历史 run 无发起人时，企业侧入口不开放。

9. **演示日策略**：新登录体系叠加在现有 demo 门禁之上，两种入口并存至 E4；是否关闭 demo 放行由负责人在 E4 决定，M1 不单方面关闭。

**待确认（M2）**：Cookie 路径取 `/` 还是 `/api`；登录页与路由守卫何时可上线（决定后端切换窗口）；旧前端在无会话时的降级表现（跳登录还是只读）。

## D2 契约版本、部署顺序与迁移编号

**结论**

1. **版本**：E1 起用 **`1.1.0-rc.1`**，E4 前定版 `1.1.0`；此后每次契约变更继续走 `-rc.N`，不预跳版。
2. **兼容策略**
   - 新端点不改变旧端点行为；`/admin/**` 的 `AdminBearer` 继续有效，旧脚本不破。
   - 响应新增字段一律**可选且默认不出现**，由新端点或显式参数启用；`additionalProperties: false` 的严格消费者不受影响。
   - 鉴权模型从「共享令牌」变为「会话 + 保留运维令牌」属**非破坏性扩展**，因此定 minor，不定 major。
3. **部署顺序（E1，固定不可调换）**：`009` 迁移 → 后端（同时接受 Cookie 与 Bearer，demo 仍放行）→ M2 登录页 → 验收 → 再讨论是否关 demo。**不做「先关后开」。**
4. **回滚**：关新入口 → 撤销全部会话 → 回退应用版本。`009` 为纯追加（新表 + 两列可空），旧版应用不受影响，**不需要 down migration**。
5. **迁移编号**
   - **009 = `users_sessions_ownership`**（`app_user`、`user_session`、`enterprise.owner_user_id`、`assessment_run.user_id`）——M1。
   - **010 = `policy_discovery`**（设置、运行记录、候选、指纹）——M1。
   - 其他成员需要新号从 **011** 起，并在 E0 表登记；**开发前与每次合入前重新查最新序号**，本地与云端当前均为 `008`。
6. **类型生成**：契约先评审，合入后由 M2 生成类型并接入消费者；M1 不产出前端类型。

**待确认（M2）**：是否接受 `1.1.0-rc.1` 的版本口径；是否需要 M1 在同一 PR 内提供生成后的类型快照。

## D3 调度限制、抓取与候选轮换

**结论**

1. **周期**：最短 **6 小时**（360 分钟），默认 24 小时，可选 6/12/24/48/168；服务端回显 `limits: {minIntervalMinutes:360,maxIntervalMinutes:10080}`。
2. **唤醒**：`systemd timer` 固定每 **15 分钟**唤醒；CLI 读设置，未启用或未到 `next_run_at` 立即退出（退出码 0，不写运行记录）。
3. **超时与容量**：单页请求超时 **15s**；单次运行硬上限 **30 分钟**；单响应 **2MB**；同一站点请求间隔 **≥2s**；全局并发 **1**；单轮最多 **50** 个新候选；重定向最多 **5** 跳且每跳复检白名单。
4. **模型预算**：单次运行 **50,000 token**，单候选 **8,000 token**；超限**停止后续调用并记录 `budget_exceeded`**，不静默截断正文；用量未知（`tokensUnknown`）时标记未知并停止继续消耗，不把占位 0 当真实零费用。
5. **停机补跑**：最多补跑**一次**最近到期任务，记录 `late_by`；不追补历史周期。
6. **轮换事务**：取锁 → `UPDATE policy_candidate SET status='expired' WHERE status IN ('pending_review','extraction_failed')` → 插入新 `discovery_run` → 开始抓取，前两步同一事务。
7. **提交与过期竞争**：提交时 `SELECT … FOR UPDATE` 锁定候选；`status <> 'pending_review'` 或 ETag 过期返回 **409**，错误码 `CANDIDATE_STATE_CONFLICT`。同一候选只有一个动作能成功。
8. **失败不复活**：新一轮抓取失败时，上一批候选仍为 `expired`，页面显示失败原因，不自动恢复可提交状态。
9. **白名单**：只允许 `data/policies/source_register.csv` 中登记的官方域名及其子域；每次重定向与最终解析 IP 都复检，禁止回环、内网、链路本地地址与 DNS 重绑定。

**待确认（M3）**：首批网址列表与栏目入口样例；**待确认（M2）**：后台页面的可操作提示文案与 limits 回显方式。

## D4 完整度数据方案

**结论**

1. **计数单位**：以 `(FactKey, 事实期间)` 为一个单位，不是「18 个键各算一格」；8 个季度起止类输入与一个年度字段不混为同一事实。
2. **口径**：完整度 = 已填写的适用单位数 / 适用单位总数；`0` 与 `false` 是**已填写**；`verified=false` 不等于未填写；未知或未填不计完成；**不适用不计入分母**；分母为 0 时 `ratio=null` 并显示「不适用」。
3. **事实键全集（18）**：`region, industry, establishedDate, taxableIncome, rdExpense, rdActivity, employeeCountStart, employeeCountEnd, assetsStart, assetsEnd, revenue, equityFinancing, rdExpenseIncrease, rdExpenseRevenueRatio, rdAddDeductionClaimed, creditRecord, specificMarketSince, independentLegalEntity`。
4. **分组草案（供 M3 修订，M1 按最终清单编码）**
   - 基础信息：`region, industry, establishedDate, independentLegalEntity, specificMarketSince, creditRecord`
   - 经营与财务：`revenue, taxableIncome, assetsStart, assetsEnd, employeeCountStart, employeeCountEnd, equityFinancing, rdExpense`
   - 研发情况：`rdActivity, rdExpenseIncrease, rdExpenseRevenueRatio, rdAddDeductionClaimed`
5. **条件树节点级求值接口：本轮不做。** 图 1 使用现有 `criteria[].expression` 展示真实 AND/OR 结构，用 API-11 的**条款级**四态着色；AST 子节点没有独立结果时显式标「未提供节点结果」，不照抄父状态。理由：节点级快照是新增存储与新增求值路径，负责人 2026-11-09 12:08 只要求「按真实表达式展示结构并关联已有条件结果」。
6. **实现落点**：`VIS-01`，直接读 `enterprise_fact`，不新增表；`definitionVersion` 在 M3 签认分组与适用规则后写入响应。

**待确认（M3）**：分组是否接受；「不适用」的判定规则（哪些键在什么政策/期间下不入分母）；`creditRecord` 归组。

## D5 事件、快照与运行生命周期采集

**结论**

1. **审核完成事件**：以「发布成功」为唯一事件，写 `review_event(policy_version_id, review_revision, actor_user_id, occurred_at)`，唯一键 `(policy_version_id, review_revision)`；幂等重放不重复计数。候选的提交/丢弃**不计**审核完成。
2. **去重单位**：按 `policy_version`，一次发布 = 一个事件；同一版本被重新发布不产生第二个事件。
3. **每日待办快照**：每日 **00:05 Asia/Shanghai** 落一次 `pending_parse + pending_review` 的版本存量；缺失当天快照返回 `null`，不用次日当前值倒补。
4. **运行生命周期**：`POST /assessment-runs` 先以 `status='running'` 插入运行行（独立事务），结束后更新 `status` 与 `finished_at`。现有触发器 `guard_assessment_run_update` 已允许更新这两个字段，**无需放开其他列**；失败需记录错误类别，因此 `009`/`010` 增加可空列 `error_category` 并同步允许更新该列。
5. **旧记录**：`created_at = finished_at` 的历史记录标为**不可信耗时样本**，查询时按 `finished_at > created_at` 过滤；历史失败率不由此倒推。
6. **接口一致性**：`API-12/13` 遇到 `failed`/`unfinished` 记录返回 **409 `RUN_NOT_COMPLETED`**，不得因缺少 `assessments` 抛 500；运行列表显示真实状态。
7. **模型调用趋势**：本轮不落库，首版不做该指标（负责人 2026-11-09 12:08 已同意）。

**待确认（M3）**：「审核完成」是否等同于发布动作；`review_revision` 的取值口径（版本号还是发布次数）。
